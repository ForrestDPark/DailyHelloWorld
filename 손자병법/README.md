이 문서는 **새 세션(다른 기기·다른 클라이언트 포함)에서도 이전 대화 맥락 없이 바로 같은 작업을 이어할 수 있도록** 지금까지 확정된 프롬프트와 작업 조건을 전부 기록해둔 것이다. 사용자가 "OO구절 해석해"라고 말하면 아래 내용만 보고 그대로 실행하면 된다.

## 1. 5섹션 해석 형식

### 역할
손자병법(孫子兵法) 전문 해석 AI로서, 사용자가 구절을 입력하면 아래 확정된 5섹션 형식으로 완전한 해석을 출력한다. 모든 응답은 한국어로 한다.

**★★★★★ 전역 문체 원칙 — 서사형으로 재밌게 (사용자 요청, 2026-07-28)**: 목록·비교표처럼 구조가 고정된 부분(道·天·地·將 목록, 法 표, 주석가 목록 등)은 형식을 그대로 지키되, 그 사이사이의 설명 문장은 건조하게 사실만 나열하지 말고 이야기하듯 흐름 있게 쓴다. 인물의 실제 발언·행동·순간을 구체적으로 살려(예: 링컨의 "the key" 발언, 순욱의 편지, 허유가 격분해 진영을 뛰쳐나오는 장면) 읽는 재미를 준다. 뜻풀이·교차 설명·핵심 통찰·실생활 적용처럼 자유 서술이 허용된 모든 부분에 적용하되, 사료로 검증되지 않은 감정·대사를 지어내지는 않는다 — 실제 기록된 사실을 생동감 있게 배치하는 것이지 허구를 더하는 것이 아니다. 4번 섹션의 "이야기 형식 서사 문단"(전투 소제목 바로 아래) 규칙이 이 원칙의 대표 적용 사례다.

**★★★★★★ 페이지 상단 목차와 큰 토글 규칙 (2026-07-28 사용자 확정):** 페이지 맨 위의 생활루틴 한 줄 바로 아래에 `<table_of_contents color="gray"/>` 자동 목차를 넣어 1~5번 섹션으로 즉시 이동할 수 있게 한다. **2번 전통 주석, 3번 교차 설명, 4번 역사적 실증 사례, 5번 핵심 통찰·실생활 적용은 제목 자체를 큰 토글 헤딩으로 만들어 섹션 전체가 접혔다 펼쳐지게 한다.** 4번은 지도와 표가 많은 핵심 본문이므로 토글 기능만 적용하고 **제목 배경색은 넣지 않는다.** 1번은 기존의 원문·독음 결합 토글을 유지한다.

### ★★★★★★★ 구절 해석 페이지 최신 확정 서식 — 이후 모든 구절에 그대로 적용

아래 항목은 2026-07-28 사용자 검토를 거쳐 확정된 최종본이다. 과거 규칙에 표·문단·토글 형식이 다르게 적혀 있더라도 **이 체크리스트가 우선한다.**

1. 페이지 맨 위에는 생활루틴 한 줄과 자동 목차를 둔다.
2. 1번은 `원문+독음`이 한몸인 토글로 만들고 직역·서사형 한자 뜻풀이를 안에 넣는다.
3. 2번 전통 주석은 표가 아니라 `주석가 — 짧은 직접 해설` 목록으로 쓴다.
4. 3번 교차 설명은 손자병법 안팎의 관점을 연결하되 한문 구절마다 독음과 뜻을 붙인다.
5. 4번 역사적 실증 사례는 인물 안내판 → 지휘·편제 조직도 → 시대 세력도 → 전략지형도 → 단계별 흐름도 순으로 시작한다.
6. 4번의 道·天·地·將은 모바일에서 들여쓰기로 본문 폭이 줄지 않도록 **`항목 | 분석` 2열 전체 폭 표**로 쓴다. 첫 열은 `道 · 지기`, `天 · 타이밍`, `地 · 광협`, `將 · 지신인용엄`처럼 판단축과 세부 기준을 함께 표시한다.
7. 4번의 法은 목록으로 바꾸지 않는다. 곡제·관도·주용을 각각 전체 폭 표로 유지한다.
8. 2·3·4·5번은 섹션 전체가 접히는 큰 토글로 만든다. 4번 토글에는 배경색을 넣지 않는다.

## 2. 전략지형도·국가 위치도 (이미지) — ★★★★★★ 2026-07-28부로 제작 재개

2026-07-27의 제작 중단 지시는 사용자의 2026-07-28 최신 요청으로 대체되었다. 아래 전략지형도 절차를 다시 수행하며, 여기에 실제 지리 데이터를 사용하는 국가 위치도를 한 장씩 추가한다.

### 국가 위치도 고정 규칙

- 국가 외곽선은 Natural Earth 같은 검증 가능한 실제 지리 데이터를 사용한다. 생성형 이미지로 국경·해안선을 그리지 않는다.
- **★★★★★★ 시대 세력도 우선 — 모든 내전·군웅할거 사례의 영구 규칙:** 삼국지·후한 말처럼 여러 군벌이 병존하거나 미국 남북전쟁처럼 한 국가가 여러 정치·군사 진영으로 갈린 전역은 현대 국가 전도에 전역 위치만 찍지 않는다. 당시 주요 군벌·교전국·동맹·경계 세력의 근거지나 주별 진영을 색으로 나눈 **해당 연도의 시대 세력도**를 국가 위치도 자리에 사용한다. 현재 분석과 직접 싸우지 않은 주변 세력도 정치적 배경을 이해할 만큼 표시하고, 주인공의 진출선과 상대의 대응 방향을 같은 지도에 겹친다. 정확한 행정 국경이나 군사 점령선이 확인되지 않는 시기는 `사료상 근거지를 중심으로 단순화한 개략 세력권`, 현재 행정선을 빌린 경우에는 `현재 경계선은 위치 참조용`이라고 지도 안에 명시한다. 현대 국가 전도+점 하나 방식은 해당 시대에 내부 세력 구분이 없을 때만 사용한다.
- **경계가 불분명한 세력권의 표현:** 후한 말 군벌처럼 국경선이 고정되지 않은 세력은 선명한 원·다각형과 빈 공백으로 나누지 않는다. 핵심 근거지는 진하게, 외곽은 반투명하게 여러 겹으로 번지는 그라데이션·블러형 영향권으로 표시하고 인접 세력의 색이 자연스럽게 겹치게 한다. 지도 안에 `색이 겹치는 곳은 경합·영향권 중첩`이라고 밝혀야 한다. 반대로 미국 남북전쟁의 주별 소속처럼 정치적 경계가 명확한 사례는 주 경계를 유지하되 실제 군사 점령선과 다를 수 있음을 별도 주석으로 구분한다.

- **★★★★★★ 배치 순서 — 인물 안내판이 무조건 첫 그림:** 각 전투·전역 제목 바로 아래의 첫 그림은 반드시 `주요 인물 안내판`으로 한다. 그다음 `지휘·편제 조직도 → 국가 위치도/시대 세력도 → 전략지형도 → 단계별 전역 흐름도 → 초심자용 전역 안내`를 둔 뒤 상세 서사를 시작한다. 지도보다 사람을 먼저 보여주며, 독자가 이름도 모르는 인물과 지명을 불릿으로 먼저 만나는 구성은 금지한다. 셔먼·손책뿐 아니라 앞으로 추가하거나 개정하는 **모든 전쟁**에 같은 순서를 적용한다.
- **주요 인물 안내판:** 양측 핵심 인물을 진영별로 한눈에 구분하고, 인물의 이름과 역할을 이미지 안 또는 바로 아래에서 대응시킨다. 생성형 초상은 실제 초상 복원이 아니라 **이해를 돕는 삽화형 재현**임을 짧게 밝힌다. 얼굴이 역사적 실물과 동일하다고 단정하지 않는다.
- **인물명 진영 색상:** 이름이 많은 전역에서도 소속이 즉시 보이도록 **승군 인물명은 파란색 굵은 글씨**, **패군 인물명은 붉은색 굵은 글씨**로 통일한다. 주요 인물 안내판·조직도뿐 아니라 Notion 본문의 모든 등장 위치에 같은 색을 쓴다. 첫 등장과 핵심 행동 문장만 칠하고 중간 문단·표·목록의 반복 이름을 기본색으로 남겨서는 안 된다. 진영을 옮긴 인물은 전환 전에는 패군색, 편입 뒤에는 승군색을 적용하고 조직도의 점선 이동 화살표로 변화를 표시한다.
- **조직도와 편제:** 총사령관 → 군단·익군·별동대 → 현장 지휘관의 실선 지휘 관계를 표시한다. 독립 임무·유인·명목상 상하 관계는 점선으로 구분한다. 각 상자에는 지휘관, 부대 또는 담당 지역, 핵심 임무를 함께 적는다. 병력 수가 사료로 확인되면 병기하고, 불확실하면 추측하지 않는다.
- **전역 중 소속 변화:** 투항·귀순·재배치·지휘권 박탈처럼 소속이 바뀐 인물은 이전 진영과 새 진영을 모두 표시하고 이동 화살표로 전환을 보여준다. 손책 전역의 태사자처럼 “능력은 있었으나 처음에는 제대로 쓰이지 못했다”는 지휘 구조상의 문제도 시각화한다.
- **초심자용 전역 안내:** 상세 서사 전에 3~6문장으로 전쟁의 시대와 당사자, 총지휘관, 상대 지휘관, 목적, 주요 지명이 사람인지 도시·강·요새인지부터 설명한다. `후드`, `메이컨`, `오거스타`처럼 초심자가 정체를 모를 이름을 설명 없이 나열하지 않는다.
- **금지하는 도입:** `먼저 잡고 갈 전역의 뼈대` 같은 추상적 제목 아래 사건만 압축 나열하지 않는다. 지도와 인물·편제 안내를 먼저 보여준 뒤 서사 안에서 사건의 원인과 결과를 풀어낸다.
- **파일명:** `<전투명>_commanders.png`, `<전투명>_command_structure.png`를 기본으로 하고, 재현 가능한 합성 스크립트와 원본 이미지를 함께 GitHub에 저장한다.

### 공통 사전 조사 (두 모드 모두 필수)

1. **전투지 좌표 검색**: `"[전투명] exact location coordinates terrain Wikipedia"`, `"[전투명] battle map deployment formation"` 검색 → 위도·경도 확보, 구글맵 링크 생성(`https://maps.google.com/maps?q=[위도],[경도]`).
2. **실제 지형·포진 검증**: `"[전투명] formation deployment [winning side] [losing side]"`, `"[전투명] terrain elevation hill river tactical"` 검색 → 양측 실제 포진 형태, 고도·강·언덕·협곡 수치 확인. **근거 출처 링크 반드시 제시.**
3. **전술 사실표 작성**: 지도 제작 전에 진영별 출발 위치·진격 방향·부대 종류·전투 단계·퇴각로·핵심 지형을 짧은 표로 확정한다. 이미지 생성 모델이나 코드가 이 사실표를 임의로 바꾸면 안 된다.
4. **그림 생성:** 아래의 Codex 또는 Claude 모드 중 선택된 한 가지 파이프라인만 실행한다.
5. **오류 발생 시**: ① 오류 원인 ② 당시 의도(왜 그렇게 그렸는지) ③ 수정 방향, 세 가지를 명시하고 고친다.

### A. Codex 전략지형도 모드

Codex의 이미지 생성 기능을 활용하되, 생성형 이미지가 병력 위치·화살표·한글을 자주 틀릴 수 있으므로 **지형 베이스와 전술 오버레이를 분리한 2단계 합성 방식**을 쓴다.

#### A-0. 기존 전략지형도 이미지 검색·선별 (새로 그리기 전에 필수)

- Codex의 웹 이미지 검색으로 `전투명 battle map`, `전투명 troop movements map`, `전투명 terrain tactical map` 및 한국어 검색어를 함께 검색한다. 한국어 자료를 우선하되, 도식의 품질과 사료 신뢰성이 더 높은 외국어 자료도 포함한다.
- 검색 결과에서 **진영·방향·단계가 명확하고 지형과 기동을 함께 보여주는 지도**를 우선한다. 단순 인물화·전투 장면·관광지도·출처 없는 재가공 이미지는 제외한다.
- 후보 이미지는 원본 페이지를 열어 제목·제작자/기관·설명·라이선스·전투 단계가 현재 분석과 일치하는지 확인한다. 검색 썸네일만 보고 채택하지 않는다.
- 출처 우선순위: 박물관·기록관·대학·정부/군사사 기관 → Wikimedia Commons의 퍼블릭도메인/CC 자료 → 신뢰할 수 있는 역사 연구·교육 사이트 → 기타 출처.
- **재사용 가능한 이미지(PD·CC 등)**는 원본 파일을 `손자병법/reference_battle_maps/<전투명>_<출처축약>.<확장자>`에 저장하고, 출처 URL·저작자·라이선스를 같은 폴더의 `SOURCES.md`에 기록한 뒤 GitHub raw URL로 노션에 삽입한다.
- **저작권이나 재사용 조건이 불명확한 이미지**는 다운로드·재업로드하지 않는다. 노션에는 원본 페이지 링크와 출처 표기만 넣고, 외부 임베드가 명시적으로 허용되는 경우에만 원본 URL을 임베드한다.
- 이해에 실질적으로 도움이 되는 자료만 전투당 최대 3개까지 고른다. 비슷한 지도를 수량만 늘려 붙이지 않는다.
- 좋은 기존 전략도가 있더라도 Codex판 생성은 생략하지 않는다. 기존 지도는 사료·비교 자료, Codex판은 현재 구절의 핵심 기동을 한국어로 재구성한 설명도라는 역할로 구분한다. 사용자가 명시적으로 “기존 지도만”을 요청한 경우에만 생성을 생략한다.

노션 삽입 순서:
1. `### 기존 전략지형도 참고자료`
2. 선별 이미지와 `제목 — 제작자/기관 · 라이선스 · [원문 출처](URL)` 캡션
3. 각 이미지 아래에 **“이 지도에서 볼 것”**을 한 문장으로 설명
4. `### Codex판 전략지형도`
5. Codex가 생성·합성한 최종 지도

#### A-1. 지형 베이스 생성

- `imagegen`의 기본 내장 이미지 생성 도구를 사용한다. 임의의 외부 이미지 API나 일회용 SDK 스크립트로 대체하지 않는다.
- 용도 분류는 `scientific-educational` 또는 `infographic-diagram`으로 지정한다.
- 입력 프롬프트에는 공통 사전 조사에서 검증한 시대·지역·계절·지형·수계·도로·취락·시점만 넣는다.
- 결과물은 **위에서 비스듬히 내려다본 3/4 조감도 또는 정사영에 가까운 전술 지도 베이스**로 만든다. 장식적인 판타지 풍경화가 아니라 지형의 높낮이·통로·병목·퇴로가 한눈에 읽혀야 한다.
- 베이스에는 글자·숫자·범례·화살표·부대 아이콘·국기·병사 무리를 생성하지 않는다. 이미지 모델이 잘못된 문자를 그리는 문제를 막기 위해 **텍스트 없는 지형만** 생성한다.
- 스타일: 정교한 군사사 박물관 전시 지도, 자연스러운 지표 질감, 절제된 색, 명확한 고도 음영, 강·도로·숲·산맥의 구분, 과도한 안개·불꽃·영화적 효과 금지.
- 생성 결과를 직접 시각 검수한다. 강의 위치, 협곡 방향, 고지와 저지, 공격 가능한 통로가 사실표와 다르면 한 번의 표적 수정 프롬프트로 다시 생성한다.
- 선택한 베이스는 프로젝트 안의 `손자병법/generated_bases/<전투명>_codex_base.png`로 복사해 보존한다. 기본 생성 폴더에만 남겨두지 않는다.

권장 프롬프트 골격:
```text
Use case: scientific-educational
Asset type: historical battle terrain base for a Korean-language tactical infographic
Primary request: create an accurate terrain-only base for [전투명, 연도]
Scene/backdrop: [검증된 지형·수계·도로·취락·계절]
Style/medium: premium military-history museum map, realistic relief terrain, restrained illustrated cartography
Composition/framing: high oblique 3/4 aerial view, tactically readable, exact orientation stated
Constraints: terrain only; preserve the researched river, ridge, pass, road and settlement relationships
Avoid: all text, labels, numbers, arrows, flags, unit symbols, soldiers, explosions, fantasy scenery, watermark
```

#### A-2. 전술 정보 오버레이

- 검증된 지형 베이스 위에 Python/Pillow 또는 기존 `strategy_map_lib.py`의 텍스트·도형 헬퍼를 사용해 전술 정보를 **결정론적으로** 합성한다.
- 진영별 반투명 병력 영역, 실제 진격·우회·퇴각 화살표, 지휘관 위치, 핵심 지형 라벨, 방향표, 축척 또는 “개략도·축척 아님” 표시, 간결한 범례를 넣는다.
- **★★★★★ 핵심 지형·거점의 지도 내부 표기:** 전투의 승패를 좌우한 호수·강·능선·고개·협로·교량·철도 분기점·도시·보급로·퇴로는 제목이나 본문에만 적지 말고 **지도 내부의 해당 위치에 직접 표시**한다. 지명만 쓰지 않고 `마수리안 호수대 — 제1·2군 사이의 기동 장벽`처럼 전술적 의미를 한 줄로 덧붙인다. 가독성을 위해 결정적인 항목 2~5개만 선별하고, 위치가 논쟁적이거나 개략적이면 라벨에 `추정`·`일대`·`개략`을 명시한다.
- 부대 배치를 이미지 모델에 맡기지 않는다. 모든 위치와 방향은 공통 사전 조사의 전술 사실표에서 가져온다.
- 한글과 한자는 코드로만 렌더링한다. 한자는 기존 전역 규칙대로 독음을 병기한다.
- **★★★★★ 휴대폰 Notion 가독성 우선:** 사용자는 전략지형도를 주로 휴대폰 Notion에서 확인하므로, 2400px 폭 기준 지도 내부 핵심 라벨은 **최소 54px**, 지형·거점 보조 라벨은 **최소 48px**, 하단 요약은 **최소 42px**, 부제목은 **최소 40px**로 렌더링한다. 한 라벨은 가능하면 두 줄·줄당 14자 안팎으로 줄이고, 설명이 길면 본문으로 옮긴다. 완성본은 원본 크기뿐 아니라 **휴대폰 폭 390px로 축소한 미리보기**에서도 읽어 보고, 작거나 겹치는 글자가 있으면 크기·위치·문구를 조정한 뒤 저장한다.
- 기존의 하단 3박스 전체를 억지로 지도 안에 넣지 않는다. Codex판은 **지도를 크게 보여주는 것을 우선**하고, 하단에는 승패를 가른 핵심 3개 요인만 간결하게 둔다. 상세 道·天·地·將 분석과 法 분석은 노션 표가 담당한다.
- 출력 크기는 세로형 최소 2400×2000px, PNG로 저장한다. 최종 파일은 `손자병법/<전투명>_codex_map.png`.

#### A-3. Codex판 품질 검수

- [ ] 웹에서 기존 전략지형도 후보를 먼저 검색하고 원본 페이지까지 검증했는가
- [ ] 채택한 외부 이미지의 출처·저작자/기관·라이선스를 기록했는가
- [ ] 저작권이 불명확한 이미지를 복제하거나 재업로드하지 않았는가
- [ ] 지형 베이스가 공통 사전 조사의 지리 관계와 맞는가
- [ ] 이미지 안의 모든 글자는 코드로 합성되어 정확한가
- [ ] 양 진영의 색·라벨·화살표가 서로 혼동되지 않는가
- [ ] 결정적 지형·거점이 지도 내부의 해당 위치에 표시되고, 전술적 의미를 함께 설명하는가
- [ ] 지형·거점 라벨이 부대명·화살표·포위망과 겹치지 않고 축소 화면에서도 읽히는가
- [ ] 390px 폭 휴대폰 미리보기에서 지도 내부 라벨과 하단 핵심 요약을 확대하지 않고 읽을 수 있는가
- [ ] 전투의 결정적 기동이 첫눈에 읽히는가
- [ ] 병력 수를 점 개수로 허위 정밀하게 표현하지 않았는가
- [ ] 불확실한 배치는 “추정” 또는 “개략”으로 표시했는가
- [ ] 장식이 정보보다 앞서지 않는가
- [ ] 원본 베이스와 최종 합성본이 프로젝트 안에 모두 보존됐는가

### 화살표 규칙

def arr(x1, y1, x2, y2, color, rad=0.15, hw=4.0, tw=2.3, alpha=0.90, z=11, dash=False):

|---|---|---|
| 공격·진격 | `#ee2222`(빨강) / `#2255dd`(파랑) | 실선 |

### 이모지 사용 기준
| 이모지 | 의미 |
|---|---|
| 🐎 | 기병 (보병 scatter 대신 사용) |
| 🔥 | 전투·혼란·화공 지점 |
| ⚔ | 지휘관·전투 단위 표식 |
| 🛡 | 방어군 지휘관 |
| 🐴 | 보조 기병 표식(장수 근처) |

**★ (사용자 명시 요청) 진영 식별에 깃발/문장 이미지를 활용한다.** 각 진영(부대/국가) 표식으로 국기·군기 이미지를 쓸 수 있으면 적극 사용한다 — 근현대 국가는 유니코드 국기 이모지(🇩🇪🇫🇷🇰🇷 등)를 `pe_em()`으로 지도에 배치하거나 하단 분석 박스 헤더 옆에 곁들인다. 유니코드 국기가 없는 고대·중세 세력(로마 군단기, 게르만 부족, 조선군 깃발 등)은 (a) 사용자가 노션에 참고 이미지를 올려주면 `reference_maps/`에 저장해두고 그 시각 모티프(색상·문양)를 `T()`/도형으로 재현하거나, (b) 마땅한 유니코드 대체가 없으면 색상 구분(진영별 troops() 색)과 범례 라벨만으로 충분히 표시한다 — 억지로 무관한 이모지를 끼워넣지 말 것.

### 하단 3박스 구조
```
[좌: 패군 분석] [중: 범례] [우: 승군 분석]
```
패/승군 박스는 6행, 五事 원문 순서 그대로: **道(지기)**(+장유오위 연결) → **天(지피)**(+장유오위 연결) → **地(지형)** → **將(장수)**(智信仁勇嚴+장유오위 1줄 요약) → **法(전력+배치)**(곡제·관도·주용 1줄 요약) → **결과**(1줄 결론). 표(섹션 1, 4번 항목)는 노션 텍스트 쪽 서식이고, 지도 박스 안에는 그 요약을 1줄로 압축해서 넣는다. 행이 하나 늘었으니 `ROW_GAP` 등 박스 높이 관련 상수를 6행 기준으로 재계산할 것 — auto-fit 장치가 있지만 새 구절 작업 시 한 번 확인.

범례(중앙 박스): 2컬럼, `LB_LEG`(32) 크기로 통일, 순서는 화살표류 → 이모지류 → 마커류.

### 색상 규칙 (★ 이번 세션에서 발견한 중요 버그 — 반드시 지킬 것)
**하단 분석 박스의 헤더 색깔은 그 진영이 지도에서 실제로 그려진 병력 색깔과 반드시 일치해야 한다.** "패군=빨강/승군=파랑" 같은 고정 관례를 따로 두면 안 된다 — 지도의 병력 색과 정보박스 색이 서로 다르면 보는 사람이 아군/적군을 헷갈린다. `draw_analysis_box(..., header_color=...)`를 호출할 때, 그 진영의 `troops()` 호출에 쓴 색과 같은 계열(#ee3333쪽이면 진한 빨강 헤더, #2255dd쪽이면 진한 파랑 헤더)을 넣을 것.

### 한자 표기 규칙 (★ 사용자 명시 요청)
한자를 과도하게 쓰지 말 것. 대부분은 한글로 쓰고, 꼭 한자를 써야 할 때만(구절 자체의 핵심 용어 등) `hj('한자', '독음')` 헬퍼로 **한자 옆에 반드시 한글 독음을 병기**한다. 예: `hj('隘地','애지')` → "隘地(애지)".

### 지형 설정 시 논리적 정합성 체크 (★ 이번 세션에서 발견한 버그)
전투 개념(예: 배수진)을 그림으로 옮길 때, 병력 배치가 그 개념과 실제로 맞는지 검산할 것. 배수진은 "내 등 뒤가 강"이어야 하는데, 강을 적과 나 사이에 놓아버리면 정반대 의미(전수진, 강을 사이에 둔 대치)가 되어버린다. 적이 공격해오는 방향을 먼저 정하고, 그 반대편에 강/절벽 등 퇴로 차단 지형이 오도록 배치할 것.

### 텍스트가 박스 밖으로 넘치지 않게 하는 장치 (라이브러리에 이미 구현됨)

### 폰트 (★ 플랫폼 자동 감지 — 이번 세션에서 확정)
`fnt()`가 Apple 경로 존재 여부를 먼저 확인하고, 없으면 자동으로 Linux 경로로 폴백한다.
- **macOS (1순위)**: 본문 `/System/Library/Fonts/AppleSDGothicNeo.ttc`, 폴백(희귀 한자용, 예: 陘·圮) `/System/Library/Fonts/STHeiti Medium.ttc`, 이모지 `/System/Library/Fonts/Apple Color Emoji.ttc`(PIL `embedded_color=True`, 유효 픽셀 160/96/64/48 — 임의 크기 불가).
- **Linux (2순위, 실제 검증된 경로)**:
  - 본문: `/usr/share/fonts/truetype/noto-kr/NotoSansCJKkr-Regular.otf` — fontTools로 `.ttc`에서 KR 페이스를 추출한 standalone 파일. *(matplotlib은 `.ttc` 내부 face index를 직접 선택하지 못해서, 원 프롬프트에 있던 `/usr/share/fonts/opentype/noto/NotoSansCJK-Bold.ttc` 직접 지정 방식은 그대로 동작하지 않았다 — 반드시 추출된 standalone 파일을 써야 한다.)*
  - 폴백: `/usr/share/fonts/truetype/noto-kr/NotoSerifCJKkr-Regular.otf`
  - 이모지: `/usr/share/fonts/truetype/noto/NotoColorEmoji.ttf` — Apple과 달리 **단일 스트라이크(109px)만 지원**. `pe_em()`의 `zoom` 값을 이 크기 기준으로 비례 보정해야 실제 시각 크기가 맞는다.
  - 설치: `apt-get install -y fonts-noto-cjk fonts-noto-cjk-extra`
- 한글+누락한자가 **한 문자열에 섞여 있으면** 통짜로 폴백폰트로 넘어가서 그 안의 한글이 깨진다 → 그런 경우 `draw_title()`처럼 문자열을 스크립트별로 쪼개서 각각 그릴 것.

### ★ 국가 세력도 (사용자 명시 요청, 전략지형도와 별개인 보조 이미지)
전략지형도(전투 자체의 전술적 지형)와는 별개로, **그 시대 해당 지역의 국가·세력 구도**를 보여주는 간단한 지도를 사례마다 하나씩 더 만들어 전략지형도 바로 아래에 삽입한다. 목적은 전술이 아니라 "이 전투 당시 주변에 어떤 나라들이 있었고 서로 어떤 외교관계였는가"를 한눈에 보여주는 것.

**★ (사용자 명시 요청) 우선순위 0 — `손자병법/reference_maps/` 폴더의 사용자 검증 지도를 최우선으로 재사용한다.** 사용자가 노션에 직접 업로드(스크린샷 등)하거나 임베드한 참고 지도는 사용자 본인이 이미 품질을 확인한 것이므로, 같은 시대·지역을 다루는 **모든 미래 구절**에서 새로 찾거나 새로 그리기 전에 이 폴더부터 확인한다. 파일명은 `<시대>_<지역/출처>.jpg` 형식(예: `springautumn_period_davincimap.jpg`). 새 구절이 이미 있는 참고 지도와 시대·지역이 겹치면(예: 다른 춘추시대 전투) 그 파일을 그대로 재사용해 raw.githubusercontent.com URL로 임베드한다 — 새로 WebSearch하거나 다이어그램을 다시 그릴 필요 없음.

**★ 사용자가 노션에 새로 참고 지도를 업로드/임베드하면, 그 즉시 영구 보관한다.** 노션에 파일을 직접 업로드(붙여넣기/드래그)하면 `notion-fetch`로 볼 때 `prod-files-secure.s3....amazonaws.com/...?X-Amz-Expires=300` 형태의 **5분짜리 임시 서명 URL**로 나타난다 — 노션 자체에서는 이 URL을 매번 새로 서명해 정상적으로 보여주지만(사용자에게는 문제 없음), 내가 그 URL을 다른 세션·다른 구절에서 재사용하려면 300초 안에 다운로드해서 리포에 영구 저장해야 한다. 발견 즉시(지체 없이) `curl -o "손자병법/reference_maps/<시대>_<지역>.jpg" "<서명URL>"`로 저장하고, 이미지를 Read 도구로 열어 실제로 지도가 맞는지 확인한 뒤 git add/commit/push한다. 외부에 영구 호스팅된 안정적 URL(예: emersonkent.com처럼 만료되지 않는 링크)은 이 저장이 필수는 아니지만, 일관성을 위해 이런 것도 함께 보관해두면 좋다.

**★★ (사용자 실사례로 확정된 금지 규칙) 노션 페이지에서 발견한 이미지는, 내가 직접 넣은 것이 확실하지 않은 한 절대 임의로 지우지 않는다.** 九地篇 4구절 작업 중 사용자가 직접 업로드한 지도+로마군 깃발 이미지를 "에이전트가 남긴 스트레이 임베드"로 착각해 삭제한 사고가 실제로 발생했다 — 삭제 후에는 임시 서명 URL이 이미 소실돼 복구 불가능했고, 사용자가 재업로드해야 했다. 알 수 없는 이미지·주석·캡션을 페이지에서 발견하면: (1) 먼저 사용자에게 의도된 것인지 물어본다, (2) 확실히 내가(또는 이 세션의 백그라운드 에이전트가) 방금 실수로 넣었다고 스스로 검증할 수 있는 경우에만 예외적으로 바로 지운다. "이상해 보인다"·"내가 넣으라고 한 적 없다" 정도의 판단만으로는 삭제 사유가 되지 않는다 — 사용자가 별도로 추가한 참고자료일 가능성을 항상 먼저 고려할 것.

**우선순위 1 — 위 0번에 해당하는 기존 참고 지도가 없으면, 실제 역사지도를 새로 찾는다.** WebSearch/WebFetch로 위키미디어 커먼즈 등에서 그 시대·지역의 기존 역사지도(예: "Spring and Autumn period states map", "Holy Roman Empire 1630 map", "Warring States 4th century BC map")를 찾는다. 퍼블릭도메인이거나 CC 라이선스(재사용 허용)인지 반드시 확인한 뒤 다운로드해서 그대로 쓴다 — 파이썬으로 지리적으로 정확한 지도를 새로 그리는 것보다 실제 역사지도를 쓰는 쪽이 항상 우선이다. 이미지 출처(라이선스 포함)를 기록해둔다.

**★ 이 세션에서 확인된 환경 제약**: 이 실행 환경의 네트워크 정책이 `commons.wikimedia.org`·`en.wikipedia.org`·`upload.wikimedia.org` 등 위키미디어 계열 접속을 프록시 단에서 차단한다(WebFetch 403, `curl "$HTTPS_PROXY/__agentproxy/status"`로 확인 가능). 이 때문에 실제 지도 파일을 **다운로드**하는 것은 이 환경에서는 보통 불가능하다 — 우회 시도하지 말고 바로 아래 조치로 넘어갈 것.

**우선순위 1-보완 — 다운로드가 막히면 링크만이라도 반드시 추가한다.** WebSearch(WebFetch와 달리 차단되지 않음)로 그 시대·지역의 실제 역사지도가 있는 페이지 URL을 찾아, 세력도 다이어그램 이미지 바로 아래에 텍스트 링크로 추가한다 — 예: `*실제 역사지도 링크: [지도 제목 — 출처](URL)*`. 이미지로 못 넣어도 사용자가 클릭해서 실제 지도를 볼 수 있게 링크는 반드시 남긴다.

**★ (사용자 확인·중요 발견) 우선순위 1-보완-B — 실제 지도의 "직접 이미지 파일 URL"(.jpg/.png/.svg 등으로 끝나는 URL)을 찾으면 다운로드 없이 바로 노션에 `![](이미지URL)`로 임베드한다.** 브라이텐펠트 사례에서 사용자가 `https://www.emersonkent.com/images/thirty_years_war_1630.jpg`를 실제 역사지도 링크 바로 아래에 직접 이미지 임베드로 추가했고, 이것이 정상 작동함을 확인했다 — 이 환경의 프록시 차단은 **내(Claude)가 직접 그 URL을 WebFetch/curl로 열람·다운로드하려 할 때만** 걸리며, 노션에 `![](URL)`로 임베드해두면 노션 서버가 그 URL을 직접 렌더링하므로 내 프록시 차단과 무관하게 정상적으로 보인다. 따라서 앞으로는(유럽 전투뿐 아니라 모든 지역) WebSearch로 그 시대·지역 실제 지도의 **직접 이미지 파일 URL**을 찾는 것을 최우선 시도로 삼는다 — 찾으면 (a) 세력도 자리에 그 URL을 `![국가 세력도 — <설명>](이미지URL)`로 바로 임베드하고 (b) 우선순위 1-보완의 텍스트 링크(원본 페이지)도 그 아래에 함께 남긴다. 이미지 자체를 내가 열람해 내용을 검증할 수는 없으므로(프록시 차단), URL 자체가 지도/지리 관련 파일명·경로(예: `map`, `_map.jpg`, `/images/`)를 갖고 있는지, 그리고 페이지 검색 스니펫상 실제 역사지도로 보이는지로 판단한다. 이 방법으로 실제 지도를 못 구할 때만 아래 우선순위 2(직접 제작한 세력도 다이어그램)로 넘어간다.

**★ (사용자 명시 요청) 링크 언어 우선순위 — 한국어 최우선.** 사용자가 한국인이므로 이 링크는 **한국어로 된 웹페이지를 최우선으로** 찾는다 (한국어 위키백과, 나무위키, 다빈치맵(davincimap.co.kr) 같은 한국어 역사지도 서비스 등). 한국어 소스가 없거나 품질이 낮을 때만 후순위로 영어 → 중국어 또는 일본어(사례의 지역·시대에 더 적합한 쪽) 소스를 추가한다. 표기 시 언어를 괄호로 명시: `*실제 역사지도 링크(한국어 우선): [한국어 소스](URL) · (영어) [영어 소스](URL)*`. 원래는 구글 이미지 검색으로 지도 이미지를 직접 눈으로 확인하고 고르는 것이 이상적이지만, **이 환경은 `google.com` 자체가 프록시 단에서 차단**되어 있고(`curl "$HTTPS_PROXY/__agentproxy/status"`로 확인), `ko.wikipedia.org`·`namu.wiki`를 포함한 대부분의 외부 도메인이 WebFetch/curl로는 직접 열람이 막혀 있다 — WebSearch 결과(제목·스니펫)만으로 후보를 고르고, 실제 이미지 유무를 직접 확인하지 못했다는 점을 인지한 채 진행한다. 우회 시도하지 말 것.

**우선순위 2 — 실제 지도(직접 임베드든 링크든)를 못 구하면 직접 제작(세력도/개략도)한다.** 지리적으로 정확한 지도는 만들기 어려우므로, 그 대신 **세력도(개략적 도식)** 형태로 대체한다 — 국가·세력을 단순한 도형(원·사각형)으로 표시하고, 화살표·선으로 외교관계(동맹·적대·속국·중립 등)를 표시하는 간단한 다이어그램. `strategy_map_lib.py`의 정교한 전략지형도 스펙을 그대로 따를 필요 없이, 훨씬 단순한 별도 스크립트(`powermap_<전투명>.py` 등)로 충분 — 배경색·범례 정도만 기존 스타일과 통일하면 된다. 우선순위 1-보완-B(직접 이미지 URL 임베드)가 성공하면 이 우선순위 2 다이어그램은 생략 가능하다 — 실제 지도를 이미 확보했다면 굳이 생성 다이어그램을 추가로 만들 필요는 없다.

**저장·삽입**: `손자병법/<전투명>_powermap.png` (또는 실제 지도를 그대로 쓸 경우 `<전투명>_historicalmap.png` 등 구분되는 이름)로 저장, git add/commit/push 후 raw URL로 노션 4번 섹션의 전략지형도 이미지 바로 아래에 `![국가 세력도](raw_url)` 형식으로 추가하고, 그 바로 다음 줄에 위 1-보완의 실제 역사지도 링크를 텍스트로 추가한다.

### ★★ (사용자 명시 요청, 2026-07-23 확정) 표는 페이지 폭 전체로 넓힌다

```

### ⚠️ 노션 페이지링크 삽입 시 반드시 알아야 할 것
`notion-create-pages`로 페이지를 만들면 그 페이지의 `<page url="...">` 블록이 **부모 페이지 맨 끝에 자동으로 붙는다.** 이걸 원하는 토글 안으로 옮겨야 하며, **반드시 실제 `<page url="...">` 태그로 옮긴다 (마크다운 링크 `[text](url)`로 대체하지 말 것) — 그래야 토글 안에 진짜 자식 페이지로 중첩된다.** 마크다운 링크로 넣으면 API는 에러 없이 성공 응답을 주지만, 실제 페이지 블록은 여전히 맨 끝에 그대로 남아있고 토글 안에는 하이퍼링크 텍스트만 생긴다(2026-07-23 세션에서 이렇게 잘못 처리해 사용자가 "밑에 있네"라고 직접 발견 — 사용자가 수동으로 옮기겠다고 해서 그 건은 그대로 둠). `<page url="...">` 태그로 직접 옮기려 하면 API가 다음처럼 명확히 알려준다: *"Cannot add a page by using the corresponding tag with a URL... To move a page within an existing page, deliberately move its existing tag within the markdown by removing it from the old location and reinserting it in the new location... Use two contentUpdates in the same updatePage call if needed."*

**★★★ (2026-07-24 세션에서 실전 검증·확정) 반드시 한 번의 `update_content` 호출 안에 content_updates 두 개를 같이 넣을 것 — 두 번의 별도 호출로 나누면(1차: 삽입, 2차: 삭제) "이미 존재하는 자식 페이지를 삭제하려는 것이냐"는 validation_error가 난다.** (이전 세션 노트에 "반드시 두 번의 별도 호출로 나눠서 하라"고 잘못 기록되어 있었는데, 2026-07-24 세션에서 실제로 재현해보니 정반대였다 — 한 호출 안에 두 content_updates를 넣는 것이 정답이다.)
1. `content_updates` 배열에 두 개를 순서대로 넣는다:
   - **① 삭제**: 맨 끝에 자동으로 붙어있던 `<page url="...">...</page>` 블록(그 앞의 `<empty-block/>`이나 개행까지 포함해서)을 빈 문자열/개행으로 치환.
   - **② 삽입**: 원하는 토글 안(구절 번역 문단 마지막 문장 뒤, 짧고 고유한 문구를 `old_str`로 잡아서)에 **똑같은** `<page url="새페이지URL">원문</page>` 태그를 삽입.
2. 이 조합 호출에는 삭제가 포함되어 있어도 `allow_deleting_content`가 필요 없었다(실제로 안 붙이고 성공함) — 아마 같은 호출 안에서 태그가 다른 위치에 재삽입되는 것을 API가 "삭제"가 아니라 "이동"으로 인식하는 것으로 보인다.
3. 성공 응답을 받아도 위치가 맞다고 단정하지 말고, 반드시 페이지를 재조회해서 새 페이지 ID 문자열이 문서에 정확히 1번만, 그리고 의도한 토글 안에 있는지 Python으로 확인한다 (거대한 페이지라 재조회 결과가 캐시된 스냅샷일 수 있으니 참고).

1. 새 구절의 5섹션 상세 페이지는 `notion-create-pages`의 parent를 **孫子兵法 최상위 페이지**(`29832a1eae808046b31bd5560346b198`)로 지정해서 만든다 — "11. 구지" 등 편 페이지가 아니다.
2. `notion-create-pages`가 새 페이지를 만들면 **그 페이지 블록이 자동으로 孫子兵法 페이지 콘텐츠 맨 끝에 붙는다** (기존 "SYSTEM"/"986180" 같은 무관한 콘텐츠 근처). 이걸 그대로 두면 안 되고, **`update_content`로 그 자동 삽입된 `<page url="...">원문</page>` 블록을 맨 끝에서 지우고, 해당 구절 토글의 원문 번역 문단 바로 뒤로 옮겨야 한다.** ★★★ 반드시 마크다운 링크(`[설명](url)`)가 아니라 **`<page url="...">원문</page>` 태그 그대로**로 옮길 것 — 이래야 토글 안에 진짜 자식 페이지 블록으로 중첩되고, 링크만 있는 게 아니라 노션 UI에서 실제 하위 페이지로 보인다. (2026-07-23 세션에서 마크다운 링크로 잘못 넣었다가 사용자가 "토글 안에 페이지로 해달라"고 재확정함 — 이후부터는 항상 `<page>` 태그 방식만 쓴다.)
3. ★★★ (2026-07-24 세션에서 재검증·정정) 이 이동은 **한 번의 `update_content` 호출 안에 content_updates 두 개를 같이 넣어서** 한다 — 두 번의 별도 호출로 나누면 오히려 "자식 페이지 삭제" 검증 오류가 난다(이전 버전의 이 문서는 반대로 적혀 있었는데, 실제 재현 결과 정정함). 두 content_updates:
   - ① 삭제: 맨 끝에 자동으로 붙은 `<page url="새페이지URL">...</page>` 블록(및 그 앞의 `<empty-block/>`)을 `old_str`로 잡아 빈 문자열로 치환.
   - ② 삽입: 토글의 원문 번역 문단 끝 문장(짧고 고유한 문구, 줄바꿈/탭 없이)을 `old_str`로 잡고, `new_str`에 그 문장 + `\n\t\t<page url="새페이지URL">원문</page>`를 추가.
   - 이 조합으로는 `allow_deleting_content` 없이도 성공한다(같은 호출 안에서 태그가 다른 곳에 재삽입되므로 API가 "이동"으로 인식하는 것으로 보임).
4. `update_content`의 `old_str`이 **토글의 닫는 `</details>` 태그나 그 앞의 탭 들여쓰기까지 포함해서 매칭하려 하면 "No matches found" 오류가 반복적으로 난다** — 실제 저장된 인덴트가 fetch가 보여주는 것과 미세하게 다를 수 있다. **해결**: `old_str`을 문장 끝(마침표 등)까지만 짧게 잡고, 줄바꿈/탭 없이 텍스트만으로 매칭한다.
5. 이 거대한 孫子兵法 페이지는 `notion-fetch`로 재조회해도 캐시된 오래된 스냅샷이 반복해서 나올 수 있다(같은 타임스탬프 반복 관찰됨). **성공 응답만으로 위치가 맞다고 단정하지 말 것** — 2026-07-23 세션에서 실제로 응답은 성공했지만 콘텐츠가 엉뚱한 위치(페이지 맨 끝)에 들어간 사례가 있었다. 반드시 재조회 후 Python으로 새 페이지 ID 문자열이 문서에서 몇 번 등장하는지, 그리고 어느 위치(토글 안인지 맨 끝인지)에 있는지 직접 확인한다.

손자병법 구절 해석의 역사적 실증 사례(4번)에 대한 전략지형도를 생성한다.
서양 전투 1장 + 동양 전투 1장, 총 2장을 생성한다.

## 사전 작업 (필수)

### Step 1 — 전투지 좌표 검색
```
검색: "[전투명] exact location coordinates terrain Wikipedia"
검색: "[전투명] battle map deployment formation"
```
- 전투지 위도·경도 확보
- 구글맵 링크 생성: `https://maps.google.com/maps?q=[위도],[경도]`

### Step 2 — 실제 지형·포진 검증
```
검색: "[전투명] formation deployment [winning side] [losing side]"
검색: "[전투명] terrain elevation hill river tactical"
```
- 실제 양측 포진 형태 문헌 확인
- 지형 특성(고도·강·언덕·협곡) 수치 확인
- **근거 출처 링크 반드시 제시**

### Step 3 — 포진 형태 검증 후 scatter 배치
- 직사각형 배열 금지 — 실제 사료 기반 포진 형태 반영
- 선봉·본대·기병·후위 위치 구분

### Step 4 — 그림 생성

### Step 5 (오류 시)
① 오류 원인 ② 당시 의도 ③ 수정 방향 명시

### 포진 형태 원칙
- **직사각형 배열 금지** — 실제 사료 기반
- 선봉: 강/적 방향 바짝, 횡대
- 본대: 선봉 뒤 종심 깊게, 강 근처일수록 조밀
- 기병: 양 측면 (남·북 끝단)
- 쐐기형: 앞쪽 좁고 뒤쪽 넓게 (depth * spread 계산)

```python
# 예: 쐐기형 포진
n = 30
depth = np.random.uniform(0, 1.2, n)
spread = np.random.uniform(-0.4, 0.4, n) * (1 - depth)  # 앞=좁, 뒤=넓

y = base_y + spread * 2.0

## 화살표 규칙
```python
def arr(x1, y1, x2, y2, color, rad=0.15, hw=4.0, tw=2.3,
        alpha=0.90, z=11, dash=False):
    ls = (0, (8, 4)) if dash else 'solid'
    ax.annotate('', xy=(x2, y2), xytext=(x1, y1),
        arrowprops=dict(
            arrowstyle=f'fancy,head_width={hw},head_length={hw*0.6},tail_width={tw}',
            color=color, alpha=alpha, mutation_scale=20,
            connectionstyle=f'arc3,rad={rad}',
            linestyle=ls), zorder=z)
```

**방향 색상 코드**
| 종류 | 색상 | 선 스타일 |
|------|------|----------|
| 공격·진격 | `#ee2222` (빨강) / `#2255dd` (파랑) | 실선 |
| 패주·퇴각 | 빨강 계열 | 점선 `dash=True` |
| 화공·특수 | `#ff6600` (주황) | 실선 |

**방향 원칙**
- 공격: 실제 진격 방향
- 위장후퇴: 공격 방향과 **같은 방향** (도망가는 척이므로)
- 패주: 반대 방향 점선
