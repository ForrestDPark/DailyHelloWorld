# session_journal — Claude·Codex 공용 작업 인계장 자동화

"클로드코덱스 이력정리" Notion 페이지(https://app.notion.com/p/3b532a1eae8080d6b6edda0d0afba7a1)에
작업 항목을 기록하고, 새 세션 시작 시 그 기록과 실제 Git 상태를 대조하는 공용 스크립트다.
`이직시스템/`, `shift_alarm/`, `일본어자막추출/` 등 어떤 서브프로젝트에서 작업하든 이 스크립트
하나로 공용 일지를 관리한다.

## 배경

2026-08-09부터 Codex가 이 페이지를 "클로드–코덱스 세션 연동 운영 규칙"(페이지 맨 위 콜아웃 참고)에
따라 손으로 기록해왔다 — KST 시간·담당 에이전트·요청·변경·검증·Git 커밋·남은 일·다음 세션 프롬프트를
매번 직접 타이핑. 2026-08-12에 이 과정 자체를 자동화해달라는 요청으로 이 스크립트를 만들었다.
**기존 형식을 그대로 따른다** — 새 포맷을 만들지 않았다.

## 사용법

### 작업(커밋) 직후 — `add`

```bash
python3 session_journal/session_journal.py add \
  --agent Claude \
  --status 완료 \
  --title "짧은 제목" \
  --request "사용자가 뭘 요청했는지" \
  --changes "실제로 뭘 바꿨는지" \
  --verification "뭘로 검증했는지(테스트, 수동 재현 등)" \
  --risks "남은 일·위험(선택)" \
  --next-prompt "다음 세션이 이어받을 때 쓸 프롬프트(선택)"
```

- `--agent`: `Claude` 또는 `Codex`
- `--status`: `완료` / `진행 중` / `대기`
- Git 커밋 해시·메시지·변경 파일·푸시 여부는 **저장소의 현재 HEAD를 자동으로 읽어** 붙인다
  (커밋 직후에 호출하는 걸 전제로 한다). 아직 커밋하지 않은 진행 중 작업을 기록할 때는
  `--no-git`을 붙인다.
- `--dry-run`을 붙이면 실제로 Notion에 쓰지 않고 결과만 미리 출력한다 — 처음 쓰는 필드
  조합이라 결과가 걱정되면 항상 먼저 `--dry-run`으로 확인할 것.
- 저장소 경로가 기본값(`session_journal/`의 부모 디렉터리, 즉 `DailyHelloWorld_/`)과
  다르면 서브커맨드 앞에 `--repo /path/to/repo`를 붙인다.

### 새 세션 시작 시 — `check`

```bash
python3 session_journal/session_journal.py check
```

한 번에 확인하는 것:
1. 일지에 마지막으로 기록된 커밋 해시(각 날짜 토글의 `Git:` 불릿에서 역파싱)
2. 로컬 `git rev-parse HEAD`와 비교해서, 일지에 없는 커밋이 있으면 `git log <일지커밋>..HEAD`로 나열
3. `git status --short`로 현재 dirty 파일 표시
4. 관련 스크립트(`shift_alarm.py`, `job_collector.py`, `contest_collector.py`,
   `company_profile.py`, `contest_tracker.py`, `extract_high_pitch_video.py`)의 실행 중 프로세스 확인

## 동작 원리·제약 (중요 — 코드 수정 전에 읽을 것)

**이 Notion 워크스페이스의 API 버전은 블록 추가 요청의 `after` 파라미터를 지원하지 않는다**
(실측: HTTP 400 `body.after should be not present`, 2026-08-09~12 여러 세션에서 반복 확인).
그래서 "새 항목이 페이지 맨 위에 온다"는 요구사항을 만족시키려면 raw Notion API로는
**페이지 최상위 자식 블록을 통째로 지우고 다시 쓰는 방법밖에 없다**. `add`가 매번 하는 일:

1. 페이지의 모든 최상위 블록(콜아웃 + 날짜별 토글)을 재귀적으로 읽어 자체 구조로 변환한다
   (`_read_block_tree`) — GET 응답을 그대로 재사용하지 않고 알려진 필드만 화이트리스트로
   뽑는다. GET 응답을 그대로 PATCH에 재사용하면 `icon: null` 같은 필드 때문에
   `validation_error`가 난다(2026-08-12 실측, 이직시스템 인덱스 작업 중 겪은 사고와 동일 원인).
2. 오늘 날짜 토글이 이미 있으면 그 토글의 자식 맨 앞에 새 항목(heading_3 + 불릿들)을 끼워
   넣고, 없으면 새 토글을 만들어 날짜 목록 맨 앞에 놓는다.
3. 페이지 최상위 자식을 전부 삭제한 뒤, 재구성한 전체 구조를 순서대로 다시 쓴다.

**기존 항목의 heading_3(시간·에이전트·제목)과 그 밑 불릿들은 부모-자식으로 중첩된 게 아니라
날짜 토글 밑에 나란히(flat sibling) 있다** — Codex가 마크다운으로 작성할 때 헤딩 다음 줄을
탭으로 들여쓰지 않아서 이렇게 됐다(2026-08-12 실측 확인). `_build_entry_nodes()`가 리스트를
반환하고 `cmd_add`가 `target_group["children"][0:0] = entry_nodes`로 끼워 넣는 것도 이
구조를 그대로 따르기 위해서다 — 임의로 "더 정돈된" 중첩 구조로 바꾸지 말 것(기존 항목들과
형식이 어긋난다).

**위험**: 페이지 전체를 지웠다 다시 쓰는 방식이라, `add` 실행 중에 Notion 앱에서 직접
페이지를 편집하고 있으면 그 편집 내용이 사라질 수 있다. 실행은 몇 초 안에 끝나지만,
동시 편집은 피할 것.
