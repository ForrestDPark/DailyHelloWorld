# 일본어자막추출

일본어 영상을 Whisper로 자막화 → 구글 번역(한국어) → 후리가나 표기 → 장면별 학습 카드 → 애플 메모 + 통합 자막(.srt) + 낭독판 EPUB 생성까지 한 번에 처리하는 파이프라인. 새 세션에서도 이 문서만 보고 바로 이어서 쓸 수 있도록 정리.

## EPUB 웹 서재 실제 배포 — 툴파챗 관리자 로그인 연동 (2026-09-06)

- 공개 주소를 `https://chat.tulpa-chat.site/epub/`로 확정하고 기존 Cloudflare
  Tunnel에 경로 기반 ingress를 추가했다. `/epub/*`만 8766 웹 리더로 보내고
  나머지 툴파챗 요청은 기존 8000 서버로 그대로 보낸다.
- `com.tulpachat.epub-reader` launchd 서비스를 설치해 로그인·재부팅 뒤에도
  자동 실행하고, 완성 EPUB 62권을 읽는다.
- 별도 서재 비밀번호는 없앴다. 같은 호스트의 `tulpa_session`을 읽기 전용 DB로
  검증하고 `users.is_owner=1`인 관리자만 책 목록·표지·본문·다운로드·진행률 API에
  접근할 수 있다. 일반 사용자와 비로그인 요청은 인증 안내만 표시한다.
- 툴파챗 워커의 공개 링크도 위 `/epub` 주소로 설정하고 워커를 재시작했다.
  일본어 선생님이 EPUB 회차를 소개하면 실제 웹 리더 책 링크를 함께 보낸다.

## EPUB 비공개 웹 서재 + 툴파챗 바로 읽기 링크 (2026-09-05)

완성된 EPUB을 Apple Books뿐 아니라 휴대폰·PC 웹에서도 볼 수 있게
`web_reader/`를 추가했다.

- `av완성작`을 우선하고 `library/`를 보조로 스캔해 표지·제목·EPUB spine 순서대로
  서재와 리더를 구성한다. 원본 EPUB을 풀어놓거나 별도 업로드하지 않는다.
- 로그인 비밀번호, HttpOnly 세션 쿠키, XHTML sandbox/CSP, ZIP 내부 경로 검증을
  적용했다. 기본 바인딩도 `127.0.0.1`이라 설정 없이 외부에 열리지 않는다.
- 책 검색, 반응형 표지 목록, 앞/뒤 페이지, 슬라이더 이동, EPUB 내려받기, 서버 DB의
  읽던 위치 저장을 지원한다. 같은 서버에 접속하면 모바일·PC 진행률이 이어진다.
- 일본어 선생님 워커는 `JP_EPUB_WEB_PUBLIC_URL`이 설정되어 있고 실제 완성 EPUB을
  찾은 경우, 오늘 처리 회차와 복습 회차를 소개할 때 파일 경로 대신 불투명 책 ID의
  `/?book=...` 링크를 별도 줄로 함께 보낸다. 링크가 없으면 주소를 지어내지 않는다.
- 실행법과 운영 환경변수는 `web_reader/README.md` 참조. 외부 도메인/Tunnel 연결은
  인증된 HTTPS 경로를 정한 뒤 별도 운영 설정으로 연결한다.

## 학습카드 누락 회차 — 원인·수정·EPUB 기반 복구 (2026-09-04~05)

툴파챗 일본어 스터디방을 실제로 테스트하다("SNOS-311 — 낮과 밤의 두 얼굴로 학습카드 전부 설명하는지 테스트해봐") 발견: 이 회차는 `library/`에 폴더 자체가 없어 학습카드를 아예 소개할 수 없었다(페르소나는 지어내지 않고 정직하게 "못 찾았다"고 답함 — 정상 동작).

- **원인 1(요약 실패도 정리됨)**: `generate_summary.py`가 AI 쿼터 소진 등으로 실패해도(`SUMMARY_OK=0`) 낭독판 EPUB 자체는 whisper 대사만으로 계속 만들어져 `av완성작`에 배포된다(★★★★★ 절대 규칙, 2026-08-07). 그런데 "성공 후 원본만 남기고 중간 작업물 영구 삭제" 단계가 `SUMMARY_OK`를 확인하지 않고 `library/<작품명>/`을 항상 통째로 지웠다 — 요약이 실패한 회차도 성공한 것처럼 뒷정리해 버린 것.
- **원인 2(성공해도 어차피 정리됨, 더 큰 원인)**: SNOS-311을 직접 조사해보니 실제로는 요약이 **성공**했었다(EPUB 안에 완전한 `summary.xhtml` 내용요약이 남아 있었음). 즉 위 "성공 후 정리" 규칙 자체가 원래 의도대로 정상 동작해 `library/`를 지운 것 — 툴파챗의 학습카드 채팅 기능(2026-09-01 추가)이 나중에 생기면서, "완성되면 중간 자료는 지운다"는 이 파이프라인의 기존 설계와 정면으로 충돌한 것이 진짜 근본 원인이다. `av완성작` 낭독판 EPUB 62개 중 35개가 이 방식으로 `library/` 폴더가 없다(학습카드 없음).
- **수정 1** (`subtitle_pipeline_body.sh`): 정리 단계가 `SUMMARY_OK==1`일 때만 `library/<작품명>/`을 지우도록 좁혔다 — 앞으로 요약이 실패한 회차만이라도 원재료가 보존되게 한다. 다만 원인 2가 보여주듯 이것만으로는 부족하다(성공한 회차도 결국 지워지므로).
- **수정 2, 핵심 — EPUB에서 역추출 복구 (`recover_study_cards_from_epub.py`, 신규, 2026-09-05)**: "라이브러리가 없으면 av완성작에서 보충해" 요청으로 확인한 사실 — 낭독판 EPUB 자체가 전체 대사(일본어 원문+후리가나+한국어 번역, 장면 대표 이미지 포함)를 페이지마다 그대로 담고 있어서, **원본 영상 없이도** `library/<작품명>/`을 완전히 새로 복구할 수 있다. `_낭독판.epub`을 압축 해제해 `OEBPS/pages/page*.xhtml`에서 대사 쌍을 파싱하고, `transcript_part{N}.jsonl`+`transcript_part{N}.md`+장면 이미지+`epub_style.css`+(있으면)`BOOK_SUBTITLE.txt`까지 원래 파이프라인이 기대하는 형식 그대로 재구성한다. 이후 `generate_summary.py`→`finalize_japanese_book.py`→`build_readaloud_epub.py`를 그대로 이어서 돌리면 학습카드 포함 낭독판이 나온다.
  - **실측 검증(SNOS-311)**: 대사 318줄·2편·15장면을 EPUB에서 완전히 복구 → `generate_summary.py`로 15장면 학습카드 전부 생성(요약문도 EPUB 원본과 내용 일치) → `finalize_japanese_book.py`로 일반 EPUB 재빌드 → `build_readaloud_epub.py`로 학습카드 음성까지 포함한 낭독판 재생성 → `av완성작`의 기존 카드 없는 파일을 이 버전으로 교체 완료. 툴파챗 채팅으로 재확인 결과 실제 데이터 기반으로 정확히 답하는 것까지 확인.
  - `subtitle_pipeline_body.sh`의 "학습카드 누락 회차 자동 복구" 단계에도 연결했다 — 매 실행 시작 시 `av완성작`의 낭독판 중 `library/`에 대응 폴더가 없는 것을 먼저 이 스크립트로 복구한 뒤, 기존 재시도 루프(`generate_summary.py` 이하)가 이어서 학습카드를 만든다.
- **남은 한계**: `av완성작`에 낭독판 파일 자체가 없는 경우(원본 영상도 EPUB도 둘 다 없음)는 이 방법으로도 복구 불가 — 그런 회차는 원본을 다시 구해야 한다.
- **일괄 복구 스크립트(`backfill_all_missing_study_cards.py`, 신규, 2026-09-06)**: "다 되면 av완성작에 바로 교체해줘" 요청 — 학습카드 없는 낭독판을 전부 찾아 위 4단계를 순서대로 돌리고 성공할 때마다 `av완성작`을 바로 교체한다. 같은 코드로 부제만 다른 회차가 여러 개 있는 경우(MIDA-764·PRED-870·RBK-132·SSIS-708 등)를 위해 `recover_study_cards_from_epub.py`에 폴더명 충돌 회피(부제까지 포함한 이름으로 대체)를 추가했고, `av완성작` 교체도 코드 접두사 glob이 아니라 지금 처리 중인 그 파일만 정확히 지우도록 했다(잘못하면 아직 처리 안 된 동일 코드의 다른 회차 파일이 같이 삭제될 뻔함). `find_missing()`은 폴더 존재 여부가 아니라 `scene_study_cards.json` 유효성으로 판정해, 배치가 중간에 죽어도(실측: Codex/Claude 양쪽 다 AI 쿼터 소진으로 8개 처리 후 중단) 재실행 시 대사 원재료가 이미 복구된 회차를 다시 복구하려다 실패하지 않고 그대로 이어서 `generate_summary.py`부터 재시도한다.
  - **1차 실행 결과**: 33개 대상 중 8개 처리 후 AI 쿼터 소진, 성공 5개·실패 3개(그중 2개는 이후 재실행으로 회복). 나머지는 쿼터가 회복되는 대로 재실행하면 이어서 처리된다.
- **★★ 중요 부작용 발견 및 수정 — "오늘 새로 처리한 회차" mtime 오판**: 위 배치로 32개 회차의 `library/` 파일을 한꺼번에 다시 쓰면서 파일 mtime이 전부 "오늘"이 됐고, `load_jp_subtitle_state()`의 mtime 기반 "오늘 새로 처리한 회차" 판정이 이 32개를 전부 오늘 새로 처리한 것으로 오판하는 사고로 이어질 뻔했다(실행 전에 발견해 배포 전 수정). `persona_worker.py`를 mtime 대신 날짜별 스냅샷(`.known_titles_snapshot.json` — 그날 시작 시점의 제목 목록을 저장하고, 그 이후 새로 나타난 제목만 "오늘 새로 처리함"으로 판정) 방식으로 바꿔 EPUB 역추출 복구·백업 복원 등 어떤 이유로 mtime이 바뀌어도 영향받지 않게 했다.

## 현재 절대 규칙 (2026-08-01)

- **Notion 단계는 종료했다.** 새 페이지 생성, 이미지 업로드, 요약 동기화, Notion 토큰 확인을 실행 파이프라인과 Shift Alarm 메뉴에서 모두 사용하지 않는다. 아래 문서에 남은 Notion 관련 내용은 과거 변경 이력일 뿐 현재 동작이 아니다.
- 각 큰 장면은 **대사를 먼저 모두 보여준 뒤**, 대사 페이지와 분리된 `장면 학습 카드`를 이어서 넣는다. 카드 순서는 **주요 단어와 뜻 / 핵심 일본어 표현 / 문법·어미·뉘앙스 / 쉐도잉 추천 문장**이며, 핵심 표현은 고정 3개가 아니라 장면에서 실제로 나온 표현 중 약 10개(6~10개)를 선별한다. 내용이 많으면 카드를 2쪽 이상으로 자동 분할하며 카드와 대사가 같은 페이지에서 겹치면 안 된다.
- 후리가나는 일본어 단어·문장 전체가 아니라 **실제 한자 덩어리 위에만** `<ruby>`로 표시한다. 조사·활용 어미·히라가나·가타카나에는 후리가나를 중복 표시하지 않는다(예: `<食 위에 た>べる`, `<約束 위에 やくそく>を<守 위에 まも>る`). 본문 대사와 학습카드 모두 같은 규칙을 쓴다.
- `핵심 일본어 표현`은 2열로 나누지 않고 반드시 **한 줄에 한 항목씩 1, 2, 3… 번호순으로 세로 나열**한다. 큰 글자에서 좌우 열로 갈라져 읽는 순서가 어긋나는 구성을 금지한다.
- 핵심 표현과 쉐도잉 문장은 `일본어 — 한국어`를 같은 줄에 붙이지 않는다. **일본어를 위 줄, 한국어 해석을 바로 아래 줄**에 회색 들여쓰기와 왼쪽 구분선으로 표시한다.
- `주요 단어와 뜻`의 한자 단어에는 일본어 읽기와 뜻뿐 아니라 **한글 한자음과 각 한자의 훈**도 함께 적는다. 한자가 없는 단어에는 억지로 붙이지 않는다.
- **학습카드 TTS(★ 2026-08-13)**: 낭독판 EPUB의 학습카드에도 `▶ 단어·표현 듣기` Media Overlay를 붙인다. `주요 단어와 뜻`은 화면에 뜻·한자 정보가 함께 있어도 **일본어 표제어만** `ja-JP-NanamiNeural`로 읽는다. `핵심 일본어 표현`은 일본어 문장을 같은 일본어 음성으로 읽은 뒤 한국어 뜻을 `ko-KR-SunHiNeural`로 이어 읽는다. 재생 중인 단어/표현 항목은 본문 대사와 같은 강조색으로 표시된다. 문구·목소리·속도가 같으면 `.readaloud_cache`의 합성 음성을 재사용한다.
- 학습카드는 장면의 마지막 대사 뒤 별도 페이지로 구성하고 모든 대사 페이지는 4문장을 기본으로 한다. 대사나 학습카드가 서로 겹치거나 잘리는 구성을 금지하며 기존 낭독·문장 강조·자동 페이지 넘김은 그대로 유지한다.
- 줄거리·부제목·장면별 학습 카드는 **로컬 Codex CLI의 비대화형 실행**으로 생성한다. ## ★★★★★ 절대 규칙 — EPUB 일본어/한국어 색상 구분 (2026-07-31, 반드시 지킬 것)

**EPUB 본문에서 일본어(원문)와 한국어(번역)는 항상 색으로 구분되어야 한다 — 사용자가 둘 다 흰색이면 "자꾸 한국어만 읽고 일본어를 안 읽게 된다"고 명시적으로 요구한 핵심 요구사항이다.**

- 일본어 줄: `<p class="ja ibooks-dark-theme-use-custom-text-color">...</p>` — 라이트모드 `#000000`(검정), 다크모드 `#f5c842`(금색), 둘 다 `font-weight: bold`.
- 한국어 줄: `<p class="ko ibooks-dark-theme-use-custom-text-color">...</p>` — 라이트모드 `#808080`, 다크모드 `#777777`(둘 다 회색, 흐리게).
- CSS(`epub_style.css`, `create_epub_css()`가 생성)는 라이트 스타일을 기본으로 두고 `@media (prefers-color-scheme: dark) { ... }` 블록으로 다크모드 값만 덮어쓴다. `:root { color-scheme: light dark; }` 선언도 필수.
- **`ibooks-dark-theme-use-custom-text-color` 클래스가 핵심이다** — Apple Books 공식 EPUB 스타일 가이드(Presentation and Styling)에 따르면, 이 클래스가 없으면 Apple Books가 다크 테마에서 **모든 커스텀 글자색을 무시하고 강제로 흰색 하나로 덮어써버린다.** 색 구분용 커스텀 색을 쓰는 요소(`p.ja`, `p.ko`, `h1`, `h2.scene`, `p.scene-desc`, `div.overview h2` 등)에는 **전부** 이 클래스를 같이 붙여야 한다. pandoc 헤더는 `{.클래스1 .클래스2}` 속성 문법으로 붙인다(예: `## 장면 1 {.scene .ibooks-dark-theme-use-custom-text-color}`).
- **핵심은 대사 텍스트를 마크다운으로 쓰는 모든 곳이 반드시 이 클래스들이 붙은 raw HTML `<p>` 태그를 써야 한다는 것** — 일반 마크다운 볼드(`**text**`)나 클래스 없는 문단으로 쓰면 pandoc이 클래스를 안 붙여서 색 구분이 통째로 사라진다(2026-07-28에 `transcript_part*.md` 생성 코드가 이 실수를 했다가 발견되어 수정된 전례가 있음 — 아래 수정 이력 참조).
- **새로운 EPUB 생성 경로를 추가하거나 수정할 때마다 반드시 확인**: 만든 EPUB을 unzip해서 XHTML 안에 `class="ja ibooks-dark-theme-use-custom-text-color"`가 실제로 존재하는지, CSS에 라이트/다크 두 버전 색 규칙이 다 있는지 확인할 것. 가능하면 Apple Books에서 라이트/다크 둘 다 켜보고 눈으로 확인.
- **경위**: 2026-07-31 전수조사(`av완성작/` EPUB 26개 unzip 확인) 때는 `class="ja"`/금색 CSS가 다 있어서 "파일은 문제없다"고 결론 냈었는데, 사용자가 "Apple Books인데 Original 테마인데도 안 된다"고 재확인해줘서 더 파보니 위 Apple Books 다크모드 특수 클래스 요구사항을 놓치고 있었다. 사용자가 라이트모드로 바꾸니 정상적으로 보인 것으로 원인이 확정됨 — 이후 "라이트/다크 각각 다른 배색"을 요청받아 지금 구조로 재설계함.


**동작 원리**:
1. `ffmpeg`로 오디오를 wav(모노 16000Hz)로 추출 — `temp_<파일명>_pitch.wav`로 캐시되어 재실행 시 재사용한다. 캐시가 있어도 원본 영상과 길이가 2초 넘게 다르면 중간에 끊긴 불완전한 캐시로 판단해 다시 추출한다. 새 캐시는 `.partial.wav`로 완성한 뒤 기존 경로에 교체하므로 추출이 중단돼도 불완전한 파일을 정상 캐시로 남기지 않는다.
2. `librosa.pyin`(확률적 YIN 알고리즘)으로 프레임마다 기본주파수(pitch, Hz)를 추정 — 유성음 구간에서만 유효한 값이 나옴(무음/자음만 있는 프레임은 제외).
3. 유성음 프레임들의 pitch 분포에서 평균값과, `--top-percent`(기본 **35%**, 2026-07-24 실전 비교 후 확정) 상위 퍼센타일을 "고음 기준"으로 잡는다. **평균 자체가 아니라 분포 상위 퍼센타일을 기준으로 쓰는 이유**: 목소리 톤은 사람/장면마다 기준선이 다 달라서, 평균보다 살짝만 높아도 잡히면 거의 전체가 걸리거나 반대로 거의 안 걸릴 수 있다 — 상위 N%로 잡으면 항상 "그 영상 안에서 상대적으로 가장 높은 구간"이 뽑힌다.
   - **★ 다이나믹 레인지가 좁으면 자동으로 15%로 전환** (2026-07-24 추가, `--top-percent`를 직접 지정하지 않았을 때만): 최고 pitch와 평균 pitch의 차이가 `LOW_RANGE_GAP_HZ`(기본 200Hz) 미만이면, 35% 기준으로는 거의 절반 가까이 뽑혀버려서 "하이라이트"의 의미가 없어진다 — 이런 영상은 `LOW_RANGE_TOP_PERCENT`(기본 15%)로 자동으로 더 빡빡하게 다시 계산한다. pyin 분석 결과(times/f0/voiced_flag)는 재사용하고 퍼센타일 계산만 다시 하므로 비용이 크지 않음.
4. 기준을 넘는 프레임들을 `--max-gap`(기본 0.5초) 이내로 붙어있으면 하나의 구간으로 묶고, `--pad`(기본 **1초**)만큼 앞뒤 여유를 준 뒤, `--min-duration`(기본 1초)보다 짧은 구간은 스파이크로 보고 버린다. 메뉴바 실행에서는 목표 분량 키패드 다음에 여유 초 키패드가 열려 매번 값을 바꿀 수 있다.
5. `ffmpeg`로 각 구간을 원본 영상에서 잘라(재인코딩) `concat`으로 이어붙여 **`<파일명>_운동용_상위<퍼센트>퍼센트_<분량>분.mp4`**를 만든다. 예: `MIAA-444_운동용_상위35퍼센트_21분.mp4`. 평균·최고 주파수는 실행 로그에서만 보여주고 파일명에는 넣지 않는다. 목표 길이 자동 탐색으로 소수 기준이 선택되거나 결과가 분 단위로 딱 떨어지지 않으면 소수점 한 자리까지 표시한다. **2026-08-01부터 구간 재인코딩은 CPU `libx264` 대신 Apple `h264_videotoolbox` 하드웨어 인코더(`-q:v 65`)를 우선 사용해 발열과 CPU 부하를 줄인다.** 시작 전에 0.5초 샘플을 실제 변환해 성공 여부를 확인하며, 사용할 수 없는 환경에서는 `libx264 -preset veryfast -crf 23 -threads 2`로 자동 복귀해 CPU 사용량을 약 두 코어로 제한한다. 한 결과물 안에 서로 다른 인코더 조각이 섞이지 않도록 인코더는 모든 구간을 자르기 전에 한 번만 결정한다.
6. `bgm/` 폴더(또는 `--bgm-dir`로 지정한 폴더)에 mp3가 있으면(아래 "운동용 영상 배경음 입히기" 참고) 무작위로 골라 배경음으로 믹스한 `<위 파일명>_bgm.mp4`도 추가로 만든다.

각 영상은 `⏱️ 오디오 추출`, `⏱️ 음높이 분석`, `⏱️ 구간 인코딩·이어붙이기`, `⏱️ BGM 생성·합성·복사`, `⏱️ 작품 전체 처리시간`을 단계별로 출력한다. 폴더를 한꺼번에 처리하면 마지막에 모든 영상의 합산 작업시간도 표시한다. 중간에 결과를 재사용하거나 실패·건너뛰기로 조기 종료해도 작품 전체 처리시간은 반드시 남는다(2026-08-01).

**디스크 부족 자동 복구(2026-08-01)**: ffmpeg가 `No space left on device`(ENOSPC, 종료 코드 228)를 반환할 때만 현재 사용자의 macOS 휴지통을 영구 비우고, 실패한 불완전 조각을 삭제한 뒤 같은 명령을 한 번 자동 재시도한다. 휴지통을 비워도 공간이 부족하면 두 번째 오류를 그대로 보고하고 원본은 보존한다. 영상별로 최대 한 번만 휴지통을 비워 무한 재시도를 막는다. 새 작업을 시작할 때 같은 출력명으로 남은 불완전 합본도 먼저 삭제해 공간을 회수한다. 이 기능은 저장 공간 부족 오류에만 작동하며 다른 ffmpeg 오류에서는 휴지통을 건드리지 않는다.

### 내용 기반 EPUB 부제목 (2026-08-01 기본 규칙)

`generate_summary.py`가 전체 대사를 요약할 때 10~25자의 자연스러운 한국어 부제목도 하나 만든다. 인물 이름을 지어내거나 결말을 노출하거나 노골적인 표현을 쓰지 않고 소설·영화 제목처럼 작성하며, `library/<작품명>/BOOK_SUBTITLE.txt`에 저장한다. 이미 저장된 부제목은 요약을 다시 실행해도 바꾸지 않는다.

- Apple Books 메타데이터: `<원본명> — <부제목>`
- 낭독판 EPUB 메타데이터: `<원본명> — <부제목> 낭독판`
- 실제 파일명: `<원본명> — <부제목>_낭독판.epub`으로 표지·서재 제목과 일치
- 표지: 원본명은 흰색, 부제목은 금색으로 하단에 함께 표시
- 원본 영상명·작업 폴더명은 추적하기 쉽도록 기존 원본명을 유지
- `BOOK_SUBTITLE.txt`가 없는 기존 작품은 예전 제목 그대로 빌드 가능

**★ 재추출 시 자기 출력물 제외**: 폴더를 지정해서 처리하면 파일명에 현재 표기인 `_운동용` 또는 예전 표기인 `_고음영상`이 들어간 파일은 원본 영상 후보에서 자동으로 제외된다. 이름 변경 전에 만든 결과도 재처리되지 않는다.

**★ 동일 작업 재사용 기록**: 고음 영상 생성이 성공하면 `<원본명>_운동용_추출기록.json`에 원본 파일의 크기·수정 시각, 목표 분량, 여유 초, 분석 옵션과 완성 파일을 기록한다. 다음 실행에서 원본과 설정이 같고 완성 파일도 정상이면 WAV 추출·pitch 분석·구간 재인코딩을 모두 생략한다. 기록 기능 도입 전에 만든 영상도 파일명의 결과 분량이 현재 목표±허용오차 안에 있고 여유 초가 같으면 실제 MP4 상태를 검사한 뒤 기록을 자동 복구해 재사용한다. BGM 성공 기록도 별도로 확인하므로 BGM까지 같으면 즉시 건너뛰고, BGM 파일이나 음량 설정만 달라졌다면 기존 고음 영상은 재사용하고 BGM 합성만 다시 한다. 최종 폴더 정리 후 기록과 무BGM 영상이 `기타/`로 이동된 경우도 자동으로 찾아낸다.

**의존성**: `librosa`, `soundfile` — 스크립트 실행 시 없으면 자동으로 `pip install`(anaconda python3 기준, 다른 스크립트들이 pykakasi/edge-tts를 자동 설치하는 것과 동일한 관례). `ffmpeg`는 기존 파이프라인과 공유.

### ★ 실전 검증 및 기준값 확정 (2026-07-24)

이 도구를 만든 세션은 ffmpeg/librosa를 실행할 수 없는 클라우드 컨테이너라 합성 데이터로 단위 테스트만 했었는데, 실제 맥에서 진짜 영상(`AV3/MUDR-393.mp4`, 124분)으로 전체 파이프라인(오디오 추출 → pitch 분석 → 구간 추출 → 영상 합치기 → 배경음 믹싱)을 여러 `--top-percent` 값으로 비교 실행해서 확인함.

| `--top-percent` | 결과 |
|---|---|
| 10% (예전 기본값) | 218개 구간, 합계 320초(5분 28초) — 너무 좁게 잡힘 |
| 30% | 운동용 영상 291MB, 배경음 트랙 합계 1258.8초(약 21분) — 훨씬 풍부하게 잡힘 |
| 40%/50%/60% | 병렬 실행 중 디스크 공간 부족 + 심볼릭 링크 유실로 재현 실패(원인 미확정) — 이후 순차 실행으로 전환 |

10%는 너무 적고, 30~35% 선에서 충분히 풍부하면서도 "하이라이트"라 부를 만한 압축이 유지되는 것으로 판단해 **기본값을 35%로 확정**. 다만 대사 톤이 평탄한(다이나믹 레인지가 좁은) 영상에서는 35%가 절반 가까이 뽑혀버릴 수 있어서, 평균-최고 pitch 차이가 200Hz 미만이면 자동으로 15%로 전환하는 로직을 추가함(위 "동작 원리" 3번 참조).

배경음 믹싱도 실제 곡(`BGM_DIR`)으로 정상 동작 확인 — 여러 곡을 무작위 순서로 이어붙여 영상 길이를 채우는 로직까지 실제로 검증됨.

**주의**: `bgm/` 폴더는 저작권 있는 상업 음원을 담는 곳이라 실제 mp3는 git에 커밋하지 않는다(퍼블릭 저장소). 로컬에 자기 음원 폴더를 따로 두고 `--bgm-dir /path/to/folder`로 가리켜서 쓸 것 — 예: `--bgm-dir "/Users/forrestdpark/Desktop/BlogImage/BGM_DIR"`. `whisper_series_stream.sh`가 자동으로 이 도구를 부를 때도 이 경로를 기본값으로 쓴다(아래 참조).

### 운동용 영상 배경음 입히기

`일본어자막추출/bgm/` 폴더에 (미리 잘라놓은) mp3 파일들을 넣어두면, `extract_high_pitch_video.py`가 운동용 영상을 만든 뒤 자동으로 이어붙여서 `<파일명>_운동용_상위<퍼센트>퍼센트_<분량>분_bgm.mp4`를 추가로 생성한다. **한 mp3를 반복 재생하는 게 아니라, `bgm/` 안의 여러 mp3를 무작위 순서로 이어붙여 영상 길이만큼 채우는 방식**이다. 원본 대사 오디오는 100%로 유지하고 BGM은 기본 28%로 그 위에 얹는다. ffmpeg `amix`의 자동 정규화는 원본 음성까지 낮추므로 끄고, 마지막 limiter로 합산 피크의 클리핑만 방지한다.

**★ 2026-08-08 곡 선택 로직 재설계(회차 간 반복 방지)**: 예전엔 `build_bgm_track()` 호출 한 번(영상 하나) 안에서만 곡이 안 겹쳤다 — 영상을 여러 개 연달아 처리하면 매번 새로 셔플하다 보니 같은 곡이 자주 다시 걸려 "음악이 계속 반복되는 것 같다"는 지적을 받았다. `shift_alarm.py`의 랜덤 북마크 추천(`pick_random_bookmarks`)과 같은 패턴으로, `~/.jp_workout_bgm_history.json`에 "이미 쓴 곡" 이력을 영구 저장해서 폴더 안 모든 곡을 최소 한 번씩 다 쓰기 전에는 같은 곡이 다시 안 뽑히게 했다(`_load_bgm_history`/`_save_bgm_history`, `build_bgm_track`). 한 영상 안에서 목표 길이를 채우다가 전체 곡을 다 쓰면(모자라면) 이력을 초기화하고 새 주기를 시작 — 이 재시작도 이력 파일에 그대로 반영되므로 다음 영상에서도 이어진다. 폴더에서 곡을 지우면 이력의 해당 항목은 자동으로 무시된다(존재하는 파일만 필터링). **2026-08-10 실측 확인**: 149곡 중 54곡이 중복 없이 소진된 상태로 정상 동작 중임을 확인함.

**★ 2026-08-10 영상별 BGM 사용 기록 추가**: 위 `~/.jp_workout_bgm_history.json`은 "다음에 뭘 안 겹치게 뽑을지"만 아는 로테이션 상태값이라, "이 영상에 무슨 곡이 나왔지?"를 나중에 사람이 물어보면 답할 수 없었다(파일 경로 목록만 있고 어느 영상에 언제 썼는지가 없음). 그래서 `~/.jp_workout_bgm_usage_log.jsonl`에 영상별로 별도 기록을 남긴다(`_log_bgm_usage`, JSON Lines라 매번 끝에 한 줄만 append) — 완성 파일명·처리 시각·쓰인 곡 목록이 한 줄에 담긴다. 조회는 영상 처리 없이:

긴 플레이리스트 MP4에서 곡명과 경계를 자동 인식해 개별 MP3로 만드는 방법은 [`bgm/README.md`](bgm/README.md)의 **긴 플레이리스트 MP4를 곡별 MP3로 자동 분할** 항목을 따른다.

```bash
python3 extract_high_pitch_video.py MIAA-444.mp4

# 배경음 볼륨 조절 (기본 0.28 = 28%, 원본 대사는 100% 유지)
python3 extract_high_pitch_video.py MIAA-444.mp4 --bgm-volume 0.2

# bgm/ 대신 다른 폴더의 mp3 사용
python3 extract_high_pitch_video.py MIAA-444.mp4 --bgm-dir /path/to/other_bgm

# 배경음 없이 운동용 영상만
python3 extract_high_pitch_video.py MIAA-444.mp4 --no-bgm
```

`bgm/` 폴더가 비어있으면(아직 mp3를 안 올렸으면) 자동으로 건너뛰고 안내 메시지만 출력 — 에러 아님. mp3를 커밋해서 `bgm/`에 넣기만 하면 바로 다음 실행부터 적용됨.

## 처리 흐름

1. 선택한 폴더의 원본 영상을 모두 스캔한 뒤, **1단계에서 모든 영상의 운동용 고음 영상과 BGM 버전을 먼저 순차 생성**한다. 한 영상의 고음 추출이 실패해도 다음 영상은 계속 처리한다.
2. 모든 영상의 고음 추출 시도가 끝나면 **2단계 자막 파이프라인**을 시작해, 원본을 한 편씩 자막·번역·Notion·EPUB까지 처리한다.
3. 영상 길이가 45분(2700초) 이상이면 2편으로 분할, 아니면 통으로 처리.
4. 각 파트: ffmpeg로 오디오 추출(16kHz mono, 대역폭 필터+노멀라이즈) → `whisper_corrections.txt`의 확인 완료 교정어를 초기 프롬프트에 포함해 whisper-cli로 일본어 자막(.srt) 생성 → 파이썬 워커가:
   - 대사 약 24줄을 장면 하나로 묶고, 장면 중앙 시점에서 대표 이미지 **한 장만** 캡처
   - 구글 번역 비공식 엔드포인트로 한국어 번역
   - `pykakasi`로 한자에 후리가나 병기 (예: `漢字(かんじ)`)
   - TTS 생성과 터미널 이미지·대사 미리보기 없이 조용히 처리
   - 노션 데이터베이스에 새 페이지를 만들고 원문/번역과 Git 후처리 상태를 기록
   - 애플 메모 "LanguageStudy" 폴더에 같은 제목으로 노트 생성, 원문 텍스트 누적 기록
   - `일본어자막추출/library/<작품명>/`에 대표 이미지, 전체 대사 JSONL/Markdown, Notion manifest, `SUMMARY.md`를 저장
   - 장면 하나(대사 약 24줄)를 마칠 때마다 `장면 N/전체 · 대사 N/전체줄 · 퍼센트` 진행률을 즉시 출력
5. 파트별 자막을 시간축 보정해서 영상 전체의 통합 `.srt` 생성.
6. 초안 EPUB은 장면마다 대표 이미지 한 장만 넣고, 이미지 폭을 본문 기준 약 60%로 크게 잡는다. CSS `float`로 이미지 오른쪽과 아래에 대사가 흐르는 책형 레이아웃을 유지하며 장면 제목은 EPUB 목차에 포함된다.
7. 완성된 EPUB을 Obsidian Study 폴더에 자동 복사(있으면).
8. 오디오 캐시(`temp_*.wav`)와 자막 캐시(`temp_*.wav.srt`)는 재실행 시 재사용됨 — 지우면 처음부터 다시 처리.

`청취 불확실` 후보는 교정 사전에 넣지 않는다. 이 사전은 다음 신규 추출의 표기를 유도하며 이미 만들어진 SRT 캐시를 자동으로 다시 쓰지는 않는다.

## ★ Git → Codex 요약 → Notion → 최종 EPUB 후처리

작품별 자료는 `일본어자막추출/library/<작품명>/`에 모인다.

```text
<작품명>/
  images/part1_scene001.jpg
  transcript_part1.jsonl
  transcript_part1.md
  notion_part1.json
  SUMMARY.md
  epub_style.css
```

1. 추출이 끝나면 `sync_book_to_notion.py --images-only`가 대표 이미지 파일을 Notion File Upload API로 직접 올려 기존 작품 페이지에 본문 폭의 이미지 블록으로 추가한다. 외부 임시 URL을 이미지 주소로 저장하지 않으므로 다운로드 URL이 만료되어도 Notion이 파일을 계속 관리한다.
2. **(2026-07-28부터 자동화, 2026-07-31 구조 변경)** `generate_summary.py library/<작품명>`이 Claude Code CLI 헤드리스 모드(`claude -p`)로 `transcript_part*.jsonl`의 대사(원문/번역)만 읽고 "전체 줄거리"와 "장면별 한 줄 설명"을 자동으로 작성한다. 이미지는 안 보낸다(텍스트만으로 충분히 정확하고 빠름 — OYC-126 1650줄/69장면 실측 96초).
   - **★★★ 장면별 설명은 SUMMARY.md에 목차로 몰아넣지 않는다.** `SUMMARY.md`에는 "전체 줄거리"만 남고, 장면별 한 줄 설명은 `inject_scene_descriptions()`가 각 장면의 **제목 + 대표 이미지 바로 다음, 대사 시작 전** 위치에 직접 끼워 넣는다(`<p class="scene-desc ibooks-dark-theme-use-custom-text-color">`). 사용자가 "장면 1, 사진 나오고, 그 다음 설명" 순서를 명시적으로 요구해서 바꾼 구조 — 앞으로도 이 순서(제목 → 이미지 → 설명 → 대사)를 반드시 지킬 것, 절대로 모든 장면 설명을 앞쪽에 목차처럼 모아놓지 말 것.
   - Claude 응답에서 장면별 설명은 입력에 준 태그를 그대로 쓴 `[N편 장면 M] 설명` 형식으로 받아 정규식으로 파싱한다 — 태그 형식을 안 지키면(실제로 몇 번 발생) 한 번 더 강조해서 자동 재시도한다. 그래도 실패하면(예: Claude가 콘텐츠 성격상 응답을 거부하는 경우도 있었음 — PRED-879) 장면 설명 없이 EPUB이 만들어진다.
   - 장면별 설명은 `library/<작품명>/scene_descriptions.json`(`{"part-scene": "설명"}`)에도 저장된다 — 오디오북 챕터 제목 등 다른 스크립트가 재사용.
3. 요약이 준비되면 `python3 sync_book_to_notion.py library/<작품명>`(images-only 아닌 기본 모드)이 자동으로 실행되어 요약을 Notion에 추가하고 상태를 `완료`로 바꾼다.
4. `python3 finalize_japanese_book.py library/<작품명>`도 자동으로 실행되어 `SUMMARY.md`와 전체 대사를 합친 일반 EPUB을 내부 중간 산출물로 만든다. `SUMMARY.md`가 아직 "요약 대기 중"이면 빌드를 거부한다.
5. 일반 EPUB 빌드가 성공하면 `build_readaloud_epub.py`가 `<원본명> — <부제목>_낭독판.epub`을 만들고 작품 폴더·옵시디언·`av완성작/`에 최종 배포한다. 성공 시 배포 위치의 일반 EPUB은 제거하며, 실패했을 때만 일반 EPUB을 비상 보존한다.

위 2~4단계는 `subtitle_pipeline_body.sh`의 각 영상 처리 마지막에 자동으로 실행되므로 더 이상 수동으로 "Codex 요약해줘" 세션을 열 필요가 없다. 실패해도 파이프라인 전체가 멈추지 않고(각 단계 실패 시 경고만 출력) 다음 영상으로 넘어간다 — 실패한 작품은 나중에 위 명령어들을 그대로 수동 재실행하면 된다.

### 반대 방향: Notion에서 고친 내용을 EPUB에 반영 (`pull_notion_summary_to_epub.py`, 2026-07-31)

`generate_summary.py`가 자동으로 쓴 요약을 사용자가 Notion 페이지에서 직접 고치거나 내용을 더 보탤 수 있다. 이렇게 Notion 쪽이 최신 상태가 됐을 때, 그 내용을 로컬 `SUMMARY.md`로 가져와 EPUB을 다시 빌드하려면:

```bash
python3 pull_notion_summary_to_epub.py library/<작품명>
```

동작 방식: `notion_part1.json`의 페이지에서 전체 블록을 가져와 "책 요약" 제목 블록 다음부터 끝까지(이미지·대사 구간은 그보다 앞에 있으므로 안 걸림)를 마크다운으로 변환해 `SUMMARY.md`를 덮어쓰고, `finalize_japanese_book.py`로 EPUB을 재빌드한다. shift_alarm 메뉴바의 `🔄 Notion 요약 → EPUB 반영 (작품 폴더 선택)` 버튼으로도 실행 가능 — 완성된 EPUB을 `av완성작/`에도 자동 복사한다.

**알려진 제약**: `SUMMARY.md`가 2026-07-31부터 "전체 줄거리"만 담고(장면별 설명은 EPUB 본문에 인라인으로만 들어감 — 위 참조), Notion "책 요약" 섹션도 이 내용만 반영된다. 즉 **장면별 설명은 Notion에는 안 올라가고 EPUB에만 존재**한다 — Notion에서 요약을 고쳐서 풀백해도 장면별 인라인 설명까지 바뀌진 않는다(전체 줄거리만 갱신됨). `sync_book_to_notion.py`의 `summary_blocks()`는 `bulleted_list_item`도 지원하지만 현재 SUMMARY.md 구조상 쓰일 일이 거의 없다.

기존 freeimage.host 및 GitHub raw 이미지 방식은 제거했다. 대표 이미지는 Git에 자동 커밋하거나 공개하지 않으며 로컬 원본과 Notion 내부 파일로만 보관한다. Notion API에서 조회되는 다운로드 URL은 일시적으로 만료될 수 있지만, Notion 페이지의 이미지 파일 자체는 유지되며 페이지를 다시 열거나 조회할 때 새 URL이 발급된다.

### 표지(cover) — 최종 EPUB에서 빠지는 버그 수정 (2026-07-31)

`subtitle_pipeline_body.sh`가 만드는 "빠른" EPUB은 원본 영상에서 세로 표지를 캡처해 pandoc `--epub-cover-image`로 넣지만, 그 표지 파일(`<파일명>_work/cover.jpg`)은 원본 영상이 있는 작업 폴더에만 있고 `library/<작품명>/`에는 없었다. `finalize_japanese_book.py`(요약 자동화가 만드는 최종 EPUB)는 애초에 표지 관련 코드가 전혀 없었고, 이 최종 EPUB이 "빠른" EPUB을 덮어쓰면서 **표지가 통째로 사라지는 버그**가 있었다(사용자가 Apple Books에 표지가 안 보인다고 지적해서 발견).

수정: `subtitle_pipeline_body.sh`가 표지를 만들 때 `library/<작품명>/cover.jpg`에도 복사해두고, `finalize_japanese_book.py`가 그 경로에 파일이 있으면 `--epub-cover-image`로 붙인다. **주의**: 이미 처리가 끝난 뒤 원본 영상 파일을 지워버리면 표지를 새로 만들 수 없다 — 표지가 필요하면 원본 영상이 있을 때(자막 파이프라인이 도는 시점)만 만들어질 수 있다는 걸 기억할 것.

**2026-08-01 보강**: 기본 PATH의 Homebrew ffmpeg 8.1.1에는 `drawtext` 필터가 빠져 있어 `No such filter: 'drawtext'`로 표지 캡션 단계가 실패한 사례(IPX-588)가 있었다. 표지 생성은 `drawtext`가 포함된 `/opt/anaconda3/bin/ffmpeg`를 명시적으로 사용한다. 그래도 영상 읽기·필터 문제 등으로 표지가 만들어지지 않으면 `create_fallback_cover.py`가 `library/<작품명>/images/*.jpg` 중 한 장을 무작위로 골라 흐린 세로 배경+가로 원본 이미지+제목 패널 형태의 960×1440 JPEG 표지를 만든다. 이후 `generate_summary.py`가 확정 부제목을 금색으로 다시 입히므로 대체 표지도 최종 제목 규칙을 그대로 따른다.

### 오디오북(.m4b) 생성 — `build_audiobook.py` (2026-07-31)

```bash
# 출력: library/<작품명>/<작품명>_오디오북.m4b
```

`library/<작품명>/`은 사용자가 완성 책을 보관하는 폴더가 아니라, 자막 파이프라인이
EPUB·오디오북을 다시 만들 수 있도록 일본어 대사(JSONL), 이미지, 요약을 보존하는
**내부 원본 자료 폴더**다. 평소에는 직접 열거나 선택할 필요가 없다. shift_alarm의
`🎧 EPUB 폴더 → 오디오북(.m4b)` 메뉴에서는 `av완성작`처럼 EPUB이 들어 있는 폴더만
선택하면 된다. 연결 가능한 작품을 자동으로 찾아 같은 폴더에 오디오북을 저장한다.
예전 방식으로 생성되어 `library` 대사 원본이 남아 있지 않은 EPUB은 이유를 출력하고
건너뛴다.

실측 검증: `SONE-486`(8장면)으로 전체 파이프라인 실행 — 36초 소요, 8챕터 정상 생성, `ffprobe -show_chapters`로 챕터 타임스탬프 확인, `AtomicParsley -t`로 `stik: Audiobook` 확인.

### ★★★★ Google 번역 429 연속 실패 시 재시도 서킷브레이커 (2026-09-03)

**질문**: "Google 번역 HTTP 429... 왜 해석이 잘안되는거지? 이거 전부 dictionary화 잘되고있는거지? 혹시나 비슷한 표현이있을때 dictionary 기준으로 응용해석하게는 못하는걸까? 구글번역안되는게 너무 많다 최근에.. 이유가 뭘까?"

**진단**:
- `translate()`가 쓰는 `translate.googleapis.com/translate_a/single`은 Google의 **비공식 무료** 엔드포인트다(공식 유료 API가 아님, `googletrans` 같은 도구가 쓰는 것과 동일). 호출량이 늘면 Google이 IP 기준으로 429를 자주 건다 — 코드 버그가 아니라 무료 엔드포인트의 태생적 한계.
- "dictionary화가 안 되고 그냥 넘어가는" 걱정은 이미 시스템이 스스로 막고 있다: 실패한 문장("[번역 실패]")은 `refine_translations.py`가 검수 상한(`--max-review`)과 무관하게 **전부** Codex(실패 시 Claude)로 앞뒤 일본어 문맥과 함께 재번역하고, 그래도 남으면 그 작품의 최종 EPUB 생성 자체를 막는다(`sys.exit`). 즉 사전(`translation_memory.json`) 없이 그냥 흘려보내지는 구조가 아니다.
- "비슷한 표현을 사전 기준으로 응용 해석" 아이디어는 **일부러 넣지 않았다** — "一人でしないの?"/"一人でするの?"처럼 부정 하나 차이로 뜻이 정반대가 되는 문장이 흔해서, 유사도 기준 재사용은 티 안 나게 오역을 만들 위험이 있다. `refine_translations.py`의 문맥 기반 AI 재번역이 이미 이보다 정확하고 안전하다.
- 진짜 개선 여지는 **효율**이었다: Google이 지금 세션을 막고 있는 동안에도 문장마다 6회 지수 백오프를 그대로 반복해 문장 하나당 최대 수십 초씩 허비하고 있었다(사용자가 붙여준 로그처럼 연속 6/6 실패가 이어지는 구간). 이런 문장은 결국 `[번역 실패]`로 끝나 `refine_translations.py`로 넘어갈 뿐이라, 재시도를 오래 끄는 것 자체가 순수 낭비였다.

**변경**: `translate()`에 서킷브레이커 추가 — 연속 실패가 `TRANSLATE_CIRCUIT_BREAKER_THRESHOLD`(5문장) 이상 쌓이면 "Google이 지금 이 세션을 막고 있다"고 판단해 이후 문장은 재시도를 `TRANSLATE_CIRCUIT_BREAKER_RETRIES`(2회)로 줄인다. 번역이 한 번이라도 성공하면 카운터가 0으로 리셋되어 다시 6회 전체 재시도로 돌아간다. 최종 결과물 품질은 그대로(같은 `refine_translations.py` 경로로 복구됨) — 쓸데없이 오래 기다리는 것만 줄인다.

**실측**: `translate()`만 떼어내 `requests.get`을 항상 429를 반환하도록 가짜로 대체해 검증 — 5번째 연속 실패까지는 6회 재시도(API 호출 6회)를 그대로 쓰다가 6번째 호출부터 2회로 줄어드는 것, 그리고 성공 응답을 흉내 낸 뒤 카운터가 0으로 리셋되고 다음 실패 호출이 다시 6회를 쓰는 것까지 모두 확인함.

### ★★★ BGM 제목 표시 기능 제거 (2026-07-31)

### ★ Whisper 자막 생성 속도 튜닝 (2026-07-28)

**배경**: 위 타이밍 로그를 넣기 전부터 사용자가 자막 생성이 체감상 오래 걸린다고 지적. 사용 중인 맥은 M2(퍼포먼스 4 + 효율 4 = 8코어)이고 `whisper-cli --help` 출력으로 Metal GPU와 flash-attention이 이미 기본 활성화되어 있는 것 확인함(이 둘은 더 손댈 게 없음).

**바꾼 것** (`subtitle_pipeline_body.sh`의 whisper-cli 호출):
1. `--beam-size 5` → `--beam-size 1`(greedy). 빔서치는 매 토큰마다 후보 5개를 유지하며 디코딩해 계산량이 greedy 대비 대략 5배 가깝게 든다 — 정확도와 직결되는 트레이드오프라 사용자에게 직접 확인받고 "속도 최우선"으로 결정함. 자막처럼 짧은 발화 단위라 정확도 손실은 크지 않을 것으로 예상.
2. `-p 4`(프로세스 4개, 스레드는 명시 안 해 기본값 4) → `-p 1 -t 8`. 기존 설정은 4프로세스×4스레드=16스레드가 8코어를 나눠 쓰면서, Metal GPU는 하나뿐이라 4개 프로세스가 같은 GPU를 두고 경쟁하는 구조였다 — 프로세스 1개가 GPU와 8코어를 통째로 쓰는 쪽이 더 빠를 것으로 보고 바꿈. 이 부분은 추측 기반 변경이라, 위 `⏱ Whisper 자막 생성 소요` 로그로 실측해서 오히려 느려지면 되돌릴 것(예: `-p 2 -t 4`도 시도해볼 만함).
3. **`--vad --vad-model` 추가 (whisper.cpp 내장 VAD, Silero)**. 사용자가 "무음/신음소리 등 사람 목소리가 아닌 구간을 미리 잘라내고 whisper를 돌리면 안 되나"라고 제안함 — 처음엔 ffmpeg `silencedetect`(에너지 임계값)로 무음만 잘라 압축 오디오를 만들고 whisper 출력 타임스탬프를 원본 시간으로 되돌리는 커스텀 파이썬 코드를 짰었는데, 사용자가 "무음의 기준을 사람 목소리가 아니면 무음"으로 정정 — 에너지 임계값으로는 신음소리(에너지는 있지만 말이 아닌 발성)를 못 걸러낸다. 대신 `whisper-cli --help`에서 whisper.cpp에 이미 Silero VAD(실제로 학습된 음성 감지 모델)가 내장돼 있는 걸 발견해서 커스텀 코드를 전부 버리고 이걸로 교체함:
   - VAD 모델(`ggml-silero-v5.1.2.bin`)은 whisper.cpp 공식 저장소의 `models/download-vad-model.sh`가 가리키는 출처(`https://huggingface.co/ggml-org/whisper-vad`)에서 받아 `/opt/homebrew/share/whisper-cpp/models/`에 둔다. `subtitle_pipeline_body.sh`가 없으면 자동으로 받고, 다운로드 실패(오프라인 등) 시에도 VAD 없이 전체 오디오로 폴백해서 파이프라인이 멈추지 않게 함.
   - **실측 검증**: 무음(2초) + 220Hz 순음(신음소리를 흉내낸 비언어적 발성, 2초) + 무음(2초) + 실제 일본어 문장("こんにちは、これはテストです。", macOS `say`로 합성) + 무음(2초)으로 합성 테스트 파일을 만들어 `--vad --vad-model`로 실행 — 220Hz 톤 구간은 완전히 무시되고 실제 발화 구간(6.11~8.25초)만 정확히 잡혔다. 로그에 `Reduced audio from 163667 to 34240 samples (79.1% reduction)`로 실제 디코딩량 감소도 확인함.

### iTerm 자동화(Automation) 권한 문제 → `.command` + `open -a iTerm` 방식으로 교체 (2026-07-23, 2026-07-24 iTerm으로 재확정)

### ★★ EPUB 가독성 전면 개편 (2026-07-24)

사용자 피드백: 표지가 이상함 / 전체적으로 가독성이 없음 / 페이지당 글자 수가 너무 적음 / 1편·2편 안에서도 목차 분할이 있었으면 함. 원인과 수정 내역:

1. **표지가 깨져 보이던 원인**: EPUB 안 `cover.xhtml`을 까보면 `<image width="0" height="0">`로 박혀있었다 — ffmpeg가 만든 jpg가 표준 JFIF(APP0) 헤더 없이 저장되는 경우가 있어서 pandoc의 이미지 크기 판독기가 가로/세로를 못 읽고 0으로 처리해버린 것(`file` 명령으로는 정상 JPEG로 보여서 헷갈리기 쉬움 — pandoc이 쓰는 판독기가 더 엄격함). `sips -s format jpeg cover.jpg --out cover.jpg`로 다시 저장하면 표준 JFIF로 정규화되어 해결된다 — EPUB 재빌드 후 `cover.xhtml`에 정확한 `960x1440`이 찍히는 것 확인함.
2. **표지 이미지 자체도 교체**: 예전엔 본문에 쓰던 3장 가로 합성 썸네일(1440x270, 배너처럼 납작함)을 표지로 재사용했다. 지금은 영상에서 별도로 세로 비율(960x1440, 2:3)로 새로 캡처하고, 하단에 반투명 검은 박스 + 제목 텍스트(영상 파일명)를 `drawtext`로 입혀서 표지답게 만든다. 캡처 시점은 영상 길이의 4%(최소 5초, 최대 90초) 지점 — 도입부일 가능성이 높은 이른 시점을 고른 것.
3. **페이지당 글자 수가 적었던 원인**: 장면 이미지가 `width:100%`로 각 세트(대사 3줄)마다 화면 전체 폭을 차지해서, 화면(페이지) 한 장에 텍스트가 몇 줄 안 들어갔다. 이미지를 `38%` 폭으로 축소하고 오디오 플레이어도 `60%`로 줄여서, 같은 화면에 훨씬 많은 대사 줄이 들어가게 했다.
4. **1편/2편 안에서 목차 분할**: 8세트(대사 24줄)마다 "🎬 장면 N" 소제목을 넣어서 EPUB 목차(TOC)에서 장면 단위로 바로 이동할 수 있게 했다. **★ 함정**: 처음엔 raw HTML로 `<h2 class="scene">...</h2>`를 그냥 썼는데, pandoc의 `--toc` 목차 생성기는 마크다운 문법으로 파싱된 `Header` 노드만 인식하고 raw HTML 블록은 그냥 불투명하게 통과시켜버려서 목차에 전혀 안 잡혔다. 마크다운 네이티브 헤더 문법 `## 제목 {.scene}`(pandoc의 헤더 속성 확장 — `{.클래스}`로 CSS 클래스도 그대로 부여됨)으로 바꾸니 목차에 정상적으로 잡힘. `--toc-depth=2`도 추가해서 파트(h1)뿐 아니라 장면(h2)까지 목차에 나오게 함.
5. **개요 페이지 추가**: 각 파트 md 맨 앞(표지/제목 페이지 바로 다음)에 그 파트의 대사 문장 수·장면 수·표기 방식을 요약한 박스를 넣었다. ★ 대사 내용 자체를 AI로 요약하는 기능은 일부러 넣지 않았다 — 성인 영상 대사를 자동 요약하는 파이프라인을 만드는 것은 별개의 판단이 필요한 문제라 통계 기반 개요로 대신함.
6. **검증**: 이미 처리 완료된 `MIAA-444`, `435MFCS-058` 작업 폴더의 기존 md/이미지/오디오를 그대로 활용해(재번역 없이 텍스트만 재구성) 새 스타일로 EPUB을 다시 빌드해서 표지 치수(960x1440 정상)와 목차 중첩(파트 밑에 장면들이 하위 항목으로 들어가는 것) 둘 다 확인함.

### ★★ 대사 오디오를 "영상에서 자른 실음성" → TTS 합성으로 교체 (2026-07-24)

**문제**: 영상에서 대사 구간(`c['start']`~`c['end']`, 앞뒤 여유 0.15~0.3초)을 잘라 세트별로 이어붙이던 방식이 실제로 들어보면 문장 중간에 끊기거나 빈 공백이 많았다 — whisper가 잡은 타임스탬프가 항상 정확하진 않고, 문장 사이 간격을 그대로 이어붙이다 보니 자연스럽지 않았다.

**해결**: 세트(대사 3줄)를 하나의 문자열로 합쳐서 `edge-tts`(`ja-JP-NanamiNeural`, `-10%` 속도 — `ebook_reader.py`가 영어 TTS에 쓰는 것과 같은 라이브러리)에 통째로 넘겨 mp3를 직접 합성한다. 이러면서:
- 영상에서 개별 문장 오디오를 자르는 ffmpeg 호출, 그걸 이어붙이는 `concat_audio_clips()`, wav→mp3 변환까지 세 단계가 통째로 없어지고 TTS 합성 한 번으로 끝남(코드도 단순해짐).
- 문장 하나하나가 아니라 **세트 단위로 한 번에 합성**하는 이유: 문장별로 3번 따로 합성해서 이어붙이면 그 사이에 어색한 침묵이 생기고, 네트워크 호출도 3배로 늘어난다. 문장을 이어붙인 텍스트를 한 번에 합성하면 자연스러운 억양으로 이어진다.
- **트레이드오프**: 실제 배우 음성이 아니라 TTS 음성으로 완전히 대체된다. 실제 음성도 같이 듣고 싶다면(둘 다 넣으면 세트당 오디오 플레이어가 2개가 되어 페이지 밀도가 다시 나빠짐) 토글 방식으로 확장 가능 — 필요하면 요청할 것.
- 기존에 이미 만들어둔 작업물(`MIAA-444`, `435MFCS-058`, `AV3`의 7개)은 이번에 TTS로 재생성하지 않았다(수백~수천 건의 TTS 호출이 필요해 시간이 많이 걸림) — 실제 음성 오디오를 그대로 유지한 채 검은 화면 버그만 고쳐서 다시 빌드했다. **새로 처리하는 영상부터 TTS가 자동 적용된다.**

### ★ av2 폴더 재작업 — TTS 파이프라인 실전 검증 + 표지 생성 실패 (2026-07-24)

`av2` 폴더(`MKMP-533`, `MUDR-393`)는 급하게 만든 임시 변환 스크립트로 옛 md를 재구성했다가 실패했다 — EPUB을 열면 페이지가 5~6개밖에 없고 내용도 거의 안 보였다(정확한 원인은 못 밝혔지만, 임시 스크립트가 옛 형식을 완전히 정확하게 파싱하지 못했던 것으로 추정). **그래서 임시 변환 대신 실제 파이프라인 스크립트를 처음부터 다시 돌렸다** — whisper 자막(`.wav.srt`)과 장면 캡처는 캐시가 있어서 재사용되고, 번역+TTS+노션+메모+md 생성만 새로 진행됨.

이 과정에서 새 버그 하나 발견: **표지 생성 ffmpeg 명령이 실전 파이프라인 안에서는 조용히 실패**했다(터미널에서 똑같은 명령을 직접 실행하면 항상 성공하는데, 오래 도는 백그라운드 실행 중에는 실패 — 정확한 원인 미확정, 리소스 경합으로 추정). 표지 없이 EPUB이 만들어졌길래 수동으로 표지만 다시 만들어 끼워넣었다. 재발해도 바로 원인을 알 수 있게 `-loglevel error`로 출력을 버리던 걸 로그 파일로 남기도록 고쳤다(실패 시 `⚠️ 표지 캡처 실패 — 로그: ...` 뒤에 마지막 20줄을 바로 출력).

**검증 결과**: `MKMP-533`(76세트, 76개 TTS mp3) / `MUDR-393`(119세트, 119개 TTS mp3) 둘 다 표지(960x1440)·본문 세트 수·오디오 파일 수가 정확히 일치하는 것까지 확인함 — 실제 파이프라인으로 처음부터 다시 도는 것 자체는 정상 동작 확인됨(표지 생성만 예외적으로 방어 로직 추가).

## "일반 EPUB" 후리가나가 괄호로 그대로 노출되던 버그 (2026-09-06)

"SONE-670... 후리가나 표현이 안되고 가로에 후리가나가있지? 이러니까 읽기할때 이상하게 읽는거같아 사이트에서 확인한건데" 피드백으로 발견.

- **원인**: `generate_furigana()`가 만드는 `漢字(かんじ)` 괄호 표기는 `transcript_part*.jsonl`의 `furigana` 필드에 저장하는 내부 중간 표현이고, `build_readaloud_epub.py`(낭독판 EPUB 빌더)만 이걸 실제 `<ruby><rt>` 태그로 바꿔왔다. 그런데 `transcript_part*.md`(→ `finalize_japanese_book.py`가 pandoc으로 만드는 "일반 EPUB")는 이 변환 없이 괄호 표기를 그대로 문장에 박아넣고 있었다 — README 절대 규칙("실제 한자 덩어리 위에만 `<ruby>`로 표시")과도 어긋난 상태.
- **왜 사용자가 직접 보게 됐나**: "일반 EPUB"은 원래 낭독판 생성용 내부 재빌드 자료일 뿐인데(README, "일반 EPUB은... 내부 중간 산출물로만 사용"), `web_reader/server.py`의 서재 스캔이 `av완성작`뿐 아니라 `library/`도 폴백 경로로 함께 훑는다(`DEFAULT_FALLBACK_DIR`). 아직 낭독판이 안 만들어진 회차는 이 "일반 EPUB"이 그대로 서재에 노출되면서 괄호 표기가 화면에 보이고, 웹 읽어주기(TTS)도 괄호 안 읽기를 문장인 것처럼 그대로 읽어 발음이 이상해진다.
- **수정**: `subtitle_pipeline_body.sh`가 `transcript_part*.md`를 쓰는 두 지점 모두에서 `furigana_paren_to_ruby_html()`(신규, `build_readaloud_epub.py`의 `kanji_only_ruby()`와 동일한 로직)을 거쳐 실제 `<ruby>` 태그로 쓰도록 고쳤다. `furigana` JSONL 필드 자체는 다른 스크립트들이 괄호 형식을 그대로 기대하므로 건드리지 않았다.
- **이미 만들어진 파일 즉시 복구**: `fix_general_epub_furigana.py`(신규) — 기존 `transcript_part*.md`의 `<p class="ja">` 안 괄호 표기를 제자리에서 `<ruby>`로 치환하고(AI 호출 없음, 순수 텍스트 처리), `finalize_japanese_book.py`로 "일반 EPUB"만 재빌드한다. 이 스크립트로 당시 서재에 노출 중이던 4개 회차(SONE-670·ABF-369·GVH-694_J·OYC-126)를 즉시 고쳤다(실측: 총 4,700줄 이상 변환, 재빌드한 EPUB에서 `<ruby>` 태그 실제 존재 확인).

## "[번역 실패]"가 서재에 그대로 보이던 문제 + recover 스크립트 NFD 파일명 버그 (2026-09-06)

"완성돼서 서재에 올라간 62권 중 2권에 [번역 실패]가 그대로 남아있다... 이거 재검증해서 번역실패라는 말 안뜨게 다시시작해" 요청.

- **원인**: 구글 번역이 계속 실패하면 `"[번역 실패]"` placeholder가 남고, `refine_translations.py`가 AI(Codex/Claude)로 재검수해서 채워야 하는데 그 시점에 AI 쿼터가 소진되면 예외를 잡아 경고만 찍고 그냥 넘어간다(`remaining_failures`가 남으면 원래 `sys.exit`으로 파이프라인을 막게 설계돼 있었는데, `SQTE-704`·`MIDV-592-...`는 그 안전장치를 통과해 배포된 상태였다).
- **재검증 결과**: 오후 사이 AI 쿼터가 회복됐다. `SQTE-704`는 이미 `translation_memory.json`(다른 회차 검수로 누적된 영구 캐시)만으로 남은 실패 0건까지 자동 해결된 상태였고, `refine_translations.py` → `finalize_japanese_book.py` → `build_readaloud_epub.py`로 재빌드해 배포본을 교체했다. `MIDV-592`는 library 폴더가 아예 없어서 `recover_study_cards_from_epub.py`로 먼저 복구한 뒤 `refine_translations.py`(67문장 AI로 재검수, 잔여 0건) → `generate_summary.py` → 재빌드 순으로 처리했다. 서재 62권 전체를 다시 스캔해 `"번역 실패"`가 남은 파일이 0개임을 확인했다.
- **★ 부수 발견 — recover 스크립트의 NFD 파일명 버그**: `MIDV-592`를 복구하는 과정에서 부제가 `"무너진 동경의 오후_낭독판"`처럼 `"_낭독판"` 접미사가 안 지워진 채로 저장되는 걸 발견했다. macOS(APFS)는 한글 파일명을 NFD(자모 분해형)로 저장하는데, `os.listdir()`/`glob.glob()`으로 얻은 경로 문자열이 NFD 상태 그대로 `recover_study_cards_from_epub.py`/`backfill_all_missing_study_cards.py`의 정규식(`_낭독판\.epub$` 등)에 들어가면 NFC로 타이핑된 패턴과 바이트 단위로 달라 조용히 매칭에 실패한다(터미널에 직접 타이핑한 경로는 NFC라 이 문제가 안 보였다 — 실제 파일시스템 목록에서 얻은 경로에서만 재현됨). 두 스크립트 모두 파일명을 다루기 전에 `unicodedata.normalize("NFC", ...)`를 거치도록 고쳤다.
