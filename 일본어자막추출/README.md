- 로컬 경로: `/Users/forrestdpark/Desktop/PDG/DailyHelloWorld_/일본어자막추출/whisper_series_stream.sh`
- 원래는 macOS 단축어(Shortcuts)로 실행하던 스크립트를 그대로 저장소에 옮긴 것. 단축어 없이 터미널에서 직접 실행하거나, shift_alarm 메뉴바 앱에서도 실행 가능(아래 참조).

## 사용법

```bash
./whisper_series_stream.sh [영상 폴더 경로]   # 생략하면 현재 폴더
```

폴더 바로 아래의 `.mp4`/`.webm`/`.mkv`/`.mov` 원본 파일을 전부 찾아서 순서대로 처리한다. 영상 하나가 끝나 결과 하위 폴더로 이동될 때마다 선택 폴더를 다시 스캔하고, 아직 시도하지 않은 다음 원본을 꺼내 처리한다. 한 파일이 실패해 원본이 남더라도 같은 실행에서 무한 재시도하지 않으며, 마지막 알림에 완료 수와 시도 수를 함께 표시한다. `_운동용`과 예전 `_고음영상` 결과 파일은 원본 후보에서 제외한다. 처리 중인 진행 상황은 새 터미널 창에서 실시간으로 보여준다.

## 운동용 영상 추출 (`extract_high_pitch_video.py`) — 2026-07-23 추가

whisper 자막 파이프라인과는 완전히 독립적인 별도 도구. Notion/메모 앱/EPUB 아무것도 안 건드리고, **영상에서 오디오를 뽑아 음높이(pitch)를 분석해서, 평균보다 확연히 높은 구간만 모아 원본 영상에서 잘라 이어붙인 운동용 영상**을 만든다.

```bash
# 영상 하나 처리 (기본값: 유성음 pitch 분포 상위 35%를 고음 기준으로, 1초 미만 구간은 버림)
python3 extract_high_pitch_video.py MIAA-444.mp4

# 기준을 직접 지정 (직접 지정하면 아래 "다이나믹 레인지가 좁을 때 자동 15%로 전환" 로직은 꺼짐)
python3 extract_high_pitch_video.py MIAA-444.mp4 --top-percent 30

# 폴더 안 영상 전부 처리 (단, 이 도구 자신이 예전에 만든 결과물은 자동으로 건너뜀 — 아래 참조)
python3 extract_high_pitch_video.py ./av2/
```

**동작 원리**:
1. `ffmpeg`로 오디오를 wav(모노 16000Hz)로 추출 — `temp_<파일명>_pitch.wav`로 캐시되어 재실행 시 재사용한다. 캐시가 있어도 원본 영상과 길이가 2초 넘게 다르면 중간에 끊긴 불완전한 캐시로 판단해 다시 추출한다. 새 캐시는 `.partial.wav`로 완성한 뒤 기존 경로에 교체하므로 추출이 중단돼도 불완전한 파일을 정상 캐시로 남기지 않는다.
2. `librosa.pyin`(확률적 YIN 알고리즘)으로 프레임마다 기본주파수(pitch, Hz)를 추정 — 유성음 구간에서만 유효한 값이 나옴(무음/자음만 있는 프레임은 제외).
3. 유성음 프레임들의 pitch 분포에서 평균값과, `--top-percent`(기본 **35%**, 2026-07-24 실전 비교 후 확정) 상위 퍼센타일을 "고음 기준"으로 잡는다. **평균 자체가 아니라 분포 상위 퍼센타일을 기준으로 쓰는 이유**: 목소리 톤은 사람/장면마다 기준선이 다 달라서, 평균보다 살짝만 높아도 잡히면 거의 전체가 걸리거나 반대로 거의 안 걸릴 수 있다 — 상위 N%로 잡으면 항상 "그 영상 안에서 상대적으로 가장 높은 구간"이 뽑힌다.
   - **★ 다이나믹 레인지가 좁으면 자동으로 15%로 전환** (2026-07-24 추가, `--top-percent`를 직접 지정하지 않았을 때만): 최고 pitch와 평균 pitch의 차이가 `LOW_RANGE_GAP_HZ`(기본 200Hz) 미만이면, 35% 기준으로는 거의 절반 가까이 뽑혀버려서 "하이라이트"의 의미가 없어진다 — 이런 영상은 `LOW_RANGE_TOP_PERCENT`(기본 15%)로 자동으로 더 빡빡하게 다시 계산한다. pyin 분석 결과(times/f0/voiced_flag)는 재사용하고 퍼센타일 계산만 다시 하므로 비용이 크지 않음.
4. 기준을 넘는 프레임들을 `--max-gap`(기본 0.5초) 이내로 붙어있으면 하나의 구간으로 묶고, `--pad`(기본 **1초**)만큼 앞뒤 여유를 준 뒤, `--min-duration`(기본 1초)보다 짧은 구간은 스파이크로 보고 버린다. 메뉴바 실행에서는 목표 분량 키패드 다음에 여유 초 키패드가 열려 매번 값을 바꿀 수 있다.
5. `ffmpeg`로 각 구간을 원본 영상에서 잘라(재인코딩) `concat`으로 이어붙여 **`<파일명>_운동용_상위<퍼센트>퍼센트_<분량>분.mp4`**를 만든다. 예: `MIAA-444_운동용_상위35퍼센트_21분.mp4`. 평균·최고 주파수는 실행 로그에서만 보여주고 파일명에는 넣지 않는다. 목표 길이 자동 탐색으로 소수 기준이 선택되거나 결과가 분 단위로 딱 떨어지지 않으면 소수점 한 자리까지 표시한다.
6. `bgm/` 폴더(또는 `--bgm-dir`로 지정한 폴더)에 mp3가 있으면(아래 "운동용 영상 배경음 입히기" 참고) 무작위로 골라 배경음으로 믹스한 `<위 파일명>_bgm.mp4`도 추가로 만든다.

**★ 재추출 시 자기 출력물 제외**: 폴더를 지정해서 처리하면 파일명에 현재 표기인 `_운동용` 또는 예전 표기인 `_고음영상`이 들어간 파일은 원본 영상 후보에서 자동으로 제외된다. 이름 변경 전에 만든 결과도 재처리되지 않는다.

**★ 동일 작업 재사용 기록**: 고음 영상 생성이 성공하면 `<원본명>_운동용_추출기록.json`에 원본 파일의 크기·수정 시각, 목표 분량, 여유 초, 분석 옵션과 완성 파일을 기록한다. 다음 실행에서 원본과 설정이 같고 완성 파일도 정상이면 WAV 추출·pitch 분석·구간 재인코딩을 모두 생략한다. 기록 기능 도입 전에 만든 영상도 파일명의 결과 분량이 현재 목표±허용오차 안에 있고 여유 초가 같으면 실제 MP4 상태를 검사한 뒤 기록을 자동 복구해 재사용한다. BGM 성공 기록도 별도로 확인하므로 BGM까지 같으면 즉시 건너뛰고, BGM 파일이나 음량 설정만 달라졌다면 기존 고음 영상은 재사용하고 BGM 합성만 다시 한다. 최종 폴더 정리 후 기록과 무BGM 영상이 `기타/`로 이동된 경우도 자동으로 찾아낸다.

**의존성**: `librosa`, `soundfile` — 스크립트 실행 시 없으면 자동으로 `pip install`(anaconda python3 기준, 다른 스크립트들이 pykakasi/edge-tts를 자동 설치하는 것과 동일한 관례). `ffmpeg`는 기존 파이프라인과 공유.

### ★ 실전 검증 및 기준값 확정 (2026-07-24)

이 도구를 만든 세션은 ffmpeg/librosa를 실행할 수 없는 클라우드 컨테이너라 합성 데이터로 단위 테스트만 했었는데, 실제 맥에서 진짜 영상(`AV3/MUDR-393.mp4`, 124분)으로 전체 파이프라인(오디오 추출 → pitch 분석 → 구간 추출 → 영상 합치기 → 배경음 믹싱)을 여러 `--top-percent` 값으로 비교 실행해서 확인함.

| `--top-percent` | 결과 |
|---|---|
| 10% (예전 기본값) | 218개 구간, 합계 320초(5분 28초) — 너무 좁게 잡힘 |
| 30% | 운동용 영상 291MB, 배경음 트랙 합계 1258.8초(약 21분) — 훨씬 풍부하게 잡힘 |
| 40%/50%/60% | 병렬 실행 중 디스크 공간 부족 + 심볼릭 링크 유실로 재현 실패(원인 미확정) — 이후 순차 실행으로 전환 |

10%는 너무 적고, 30~35% 선에서 충분히 풍부하면서도 "하이라이트"라 부를 만한 압축이 유지되는 것으로 판단해 **기본값을 35%로 확정**. 다만 대사 톤이 평탄한(다이나믹 레인지가 좁은) 영상에서는 35%가 절반 가까이 뽑혀버릴 수 있어서, 평균-최고 pitch 차이가 200Hz 미만이면 자동으로 15%로 전환하는 로직을 추가함(위 "동작 원리" 3번 참조).

배경음 믹싱도 실제 곡(`BGM_DIR`)으로 정상 동작 확인 — 여러 곡을 무작위 순서로 이어붙여 영상 길이를 채우는 로직까지 실제로 검증됨.

**주의**: `bgm/` 폴더는 저작권 있는 상업 음원을 담는 곳이라 실제 mp3는 git에 커밋하지 않는다(퍼블릭 저장소). 로컬에 자기 음원 폴더를 따로 두고 `--bgm-dir /path/to/folder`로 가리켜서 쓸 것 — 예: `--bgm-dir "/Users/forrestdpark/Desktop/BlogImage/BGM_DIR"`. `whisper_series_stream.sh`가 자동으로 이 도구를 부를 때도 이 경로를 기본값으로 쓴다(아래 참조).

### ★ whisper 파이프라인과 자동 연동 (2026-07-24 추가)

`whisper_series_stream.sh`(자막/번역/EPUB 파이프라인)가 각 영상 처리 시작 시 **가장 먼저** 이 도구를 호출해서 운동용 영상(+배경음)을 만든다 — 자막/번역/EPUB 작업이 오래 걸리니, 상대적으로 빨리 끝나는 운동용 영상 결과부터 먼저 확인할 수 있게 순서를 그렇게 잡았다. `shift_alarm` 메뉴바의 `🎥 일본어 자막 추출` 버튼을 눌러도 자동으로 같이 실행된다(별도 버튼 없음).

- `BGM_DIR` 환경변수(기본값 `/Users/forrestdpark/Desktop/BlogImage/BGM_DIR`)로 배경음 폴더를 지정 — `whisper_series_stream.sh` 실행 전에 `export BGM_DIR=/path/to/folder`로 바꿀 수 있음.
- 모든 처리가 끝나면 영상별로 폴더를 정리한다:
  ```
  <파일명>/
    <파일명>.mp4                              (원본 영상)
    <파일명>.epub
    <파일명>_운동용_상위..퍼센트_..분_bgm.mp4          (배경음 입힌 운동용 영상)
    기타/
      <파일명>_운동용_상위..퍼센트_..분.mp4             (배경음 없는 버전)
      <파일명>.srt, <파일명>*.md, <파일명>_work/, <파일명>_scenes_part*/, temp_*.wav* 등
  ```
  최상위엔 바로 확인할 3개(원본/EPUB/배경음 운동용 영상)만 남기고, 나머지 작업 파일은 `기타/`로 몰아넣는다.
- 이 폴더를 나중에 다시 `whisper_series_stream.sh <파일명>/`으로 재실행해도, `_운동용`과 예전 `_고음영상` 결과는 모두 원본 영상 후보에서 자동 제외된다.

### 운동용 영상 배경음 입히기

`일본어자막추출/bgm/` 폴더에 (미리 잘라놓은) mp3 파일들을 넣어두면, `extract_high_pitch_video.py`가 운동용 영상을 만든 뒤 자동으로 이어붙여서 `<파일명>_운동용_상위<퍼센트>퍼센트_<분량>분_bgm.mp4`를 추가로 생성한다. **한 mp3를 반복 재생하는 게 아니라, `bgm/` 안의 여러 mp3를 무작위 순서로 이어붙여 영상 길이만큼 채우는 방식**이다. 다 이어붙였는데도 영상 길이가 안 채워지면 다시 셔플해서 계속 이어붙인다. 원본 대사 오디오는 100%로 유지하고 BGM은 기본 28%로 그 위에 얹는다. ffmpeg `amix`의 자동 정규화는 원본 음성까지 낮추므로 끄고, 마지막 limiter로 합산 피크의 클리핑만 방지한다.

**(2026-07-31 제거)** BGM이 바뀔 때 곡 제목("아티스트 - 곡명")을 영상 하단에 표시하는 기능이 있었으나 제거했다. libass로 제목 자막을 태우려면 영상 전체를 재인코딩해야 해서(소프트웨어 x264 → 나중에 하드웨어 videotoolbox로 바꿔봤어도) 30~40분 영상 기준 CPU를 많이 먹고 오래 걸렸는데, 실사용에서 그 표시가 딱히 필요 없다고 판단해 기능 자체를 뺐다. 지금은 오디오만 합치고 영상은 항상 스트림 복사(`-c:v copy`, 재인코딩 없음)만 하므로 BGM 믹싱이 훨씬 빠르다.

긴 플레이리스트 MP4에서 곡명과 경계를 자동 인식해 개별 MP3로 만드는 방법은 [`bgm/README.md`](bgm/README.md)의 **긴 플레이리스트 MP4를 곡별 MP3로 자동 분할** 항목을 따른다.

```bash
# bgm/ 폴더에 mp3가 있으면 기본 동작으로 자동 믹스됨 (별도 옵션 불필요)
python3 extract_high_pitch_video.py MIAA-444.mp4

# 배경음 볼륨 조절 (기본 0.28 = 28%, 원본 대사는 100% 유지)
python3 extract_high_pitch_video.py MIAA-444.mp4 --bgm-volume 0.2

# bgm/ 대신 다른 폴더의 mp3 사용
python3 extract_high_pitch_video.py MIAA-444.mp4 --bgm-dir /path/to/other_bgm

# 배경음 없이 운동용 영상만
python3 extract_high_pitch_video.py MIAA-444.mp4 --no-bgm
```

`bgm/` 폴더가 비어있으면(아직 mp3를 안 올렸으면) 자동으로 건너뛰고 안내 메시지만 출력 — 에러 아님. mp3를 커밋해서 `bgm/`에 넣기만 하면 바로 다음 실행부터 적용됨.

## 사전 준비 — macOS 키체인에 시크릿 등록 (★ 필수, 최초 1회)

이 스크립트는 노션 토큰을 **코드에 하드코딩하지 않고 macOS 키체인에서 읽는다**. 대표 이미지는 외부 이미지 호스팅이나 GitHub를 거치지 않고 Notion File Upload API로 직접 저장한다.


## 처리 흐름

1. 선택한 폴더의 원본 영상을 모두 스캔한 뒤, **1단계에서 모든 영상의 운동용 고음 영상과 BGM 버전을 먼저 순차 생성**한다. 한 영상의 고음 추출이 실패해도 다음 영상은 계속 처리한다.
2. 모든 영상의 고음 추출 시도가 끝나면 **2단계 자막 파이프라인**을 시작해, 원본을 한 편씩 자막·번역·Notion·EPUB까지 처리한다.
3. 영상 길이가 45분(2700초) 이상이면 2편으로 분할, 아니면 통으로 처리.
4. 각 파트: ffmpeg로 오디오 추출(16kHz mono, 대역폭 필터+노멀라이즈) → `whisper_corrections.txt`의 확인 완료 교정어를 초기 프롬프트에 포함해 whisper-cli로 일본어 자막(.srt) 생성 → 파이썬 워커가:
   - 대사 약 24줄을 장면 하나로 묶고, 장면 중앙 시점에서 대표 이미지 **한 장만** 캡처
   - 구글 번역 비공식 엔드포인트로 한국어 번역
   - `pykakasi`로 한자에 후리가나 병기 (예: `漢字(かんじ)`)
   - TTS 생성과 터미널 이미지·대사 미리보기 없이 조용히 처리
   - 노션 데이터베이스에 새 페이지를 만들고 원문/번역과 Git 후처리 상태를 기록
   - 애플 메모 "LanguageStudy" 폴더에 같은 제목으로 노트 생성, 원문 텍스트 누적 기록
   - `일본어자막추출/library/<작품명>/`에 대표 이미지, 전체 대사 JSONL/Markdown, Notion manifest, `SUMMARY.md`를 저장
   - 장면 하나(대사 약 24줄)를 마칠 때마다 `장면 N/전체 · 대사 N/전체줄 · 퍼센트` 진행률을 즉시 출력
5. 파트별 자막을 시간축 보정해서 영상 전체의 통합 `.srt` 생성.
6. 초안 EPUB은 장면마다 대표 이미지 한 장만 넣고, 이미지 폭을 본문 기준 약 60%로 크게 잡는다. CSS `float`로 이미지 오른쪽과 아래에 대사가 흐르는 책형 레이아웃을 유지하며 장면 제목은 EPUB 목차에 포함된다.
7. 완성된 EPUB을 Obsidian Study 폴더에 자동 복사(있으면).
8. 오디오 캐시(`temp_*.wav`)와 자막 캐시(`temp_*.wav.srt`)는 재실행 시 재사용됨 — 지우면 처음부터 다시 처리.

`청취 불확실` 후보는 교정 사전에 넣지 않는다. 이 사전은 다음 신규 추출의 표기를 유도하며 이미 만들어진 SRT 캐시를 자동으로 다시 쓰지는 않는다.

## ★ Git → Codex 요약 → Notion → 최종 EPUB 후처리

작품별 자료는 `일본어자막추출/library/<작품명>/`에 모인다.

```text
<작품명>/
  images/part1_scene001.jpg
  transcript_part1.jsonl
  transcript_part1.md
  notion_part1.json
  SUMMARY.md
  epub_style.css
```

1. 추출이 끝나면 `sync_book_to_notion.py --images-only`가 대표 이미지 파일을 Notion File Upload API로 직접 올려 기존 작품 페이지에 본문 폭의 이미지 블록으로 추가한다. 외부 임시 URL을 이미지 주소로 저장하지 않으므로 다운로드 URL이 만료되어도 Notion이 파일을 계속 관리한다.
2. **(2026-07-28부터 자동화)** `generate_summary.py library/<작품명>`이 Claude Code CLI 헤드리스 모드(`claude -p`)로 `transcript_part*.jsonl`의 대사(원문/번역)만 읽고 `SUMMARY.md`의 전체 줄거리와 장면별 목차를 자동으로 작성한다. 이미지는 안 보낸다(텍스트만으로 충분히 정확하고 빠름 — OYC-126 1650줄/69장면 실측 96초).
3. 요약이 준비되면 `python3 sync_book_to_notion.py library/<작품명>`(images-only 아닌 기본 모드)이 자동으로 실행되어 요약을 Notion에 추가하고 상태를 `완료`로 바꾼다.
4. `python3 finalize_japanese_book.py library/<작품명>`도 자동으로 실행되어 `SUMMARY.md`와 전체 대사를 합쳐 목차가 포함된 최종 EPUB을 만든다. `SUMMARY.md`가 아직 "요약 대기 중"이면 빌드를 거부한다. 이 최종 EPUB이 앞서 만든 "빠른" EPUB(줄거리 없음)을 덮어쓰고, 옵시디언 및 `/Users/forrestdpark/Desktop/BlogImage/av완성작/`(완성작을 한곳에 몰아보려고 지정한 폴더)에도 복사된다.

위 2~4단계는 `subtitle_pipeline_body.sh`의 각 영상 처리 마지막에 자동으로 실행되므로 더 이상 수동으로 "Codex 요약해줘" 세션을 열 필요가 없다. 실패해도 파이프라인 전체가 멈추지 않고(각 단계 실패 시 경고만 출력) 다음 영상으로 넘어간다 — 실패한 작품은 나중에 위 명령어들을 그대로 수동 재실행하면 된다.

기존 freeimage.host 및 GitHub raw 이미지 방식은 제거했다. 대표 이미지는 Git에 자동 커밋하거나 공개하지 않으며 로컬 원본과 Notion 내부 파일로만 보관한다. Notion API에서 조회되는 다운로드 URL은 일시적으로 만료될 수 있지만, Notion 페이지의 이미지 파일 자체는 유지되며 페이지를 다시 열거나 조회할 때 새 URL이 발급된다.

### ★★★ BGM 제목 표시 기능 제거 (2026-07-31)

**경위**: 사용자가 "고음 영상 만들 때 mp3 씌우는 게 왜 이리 CPU를 많이 먹고 오래 걸리냐"고 지적. 원인은 BGM 제목("아티스트 - 곡명")을 영상 하단에 표시하는 기능이 libass로 자막을 태우기 위해 영상 전체를 재인코딩하고 있었기 때문(제목 없이 오디오만 합칠 땐 `-c:v copy`로 재인코딩 자체가 없어 거의 즉시 끝남). 처음엔 소프트웨어(`libx264 -preset medium -crf 18`) → 하드웨어(`h264_videotoolbox`)로 바꿔서 실측 CPU 시간 약 5배 절감까지 확인했는데, 사용자가 "그 제목 표시 자체가 필요 없다"고 확인해줘서 기능을 통째로 뺐다.

같은 세션에서 "CoreText note: ... .LastResort ..." 경고 반복 출력도 같이 질문받았는데, 원인은 제목 표시용 폰트("Apple SD Gothic Neo")가 이모지 글리프를 지원하지 않아서 실제 BGM mp3 파일명에 이모지가 섞여 있으면(격리 테스트로 재현 확인 — 이모지 있을 때만 발생) 프레임마다 폰트 폴백 경고가 났던 것. 기능 자체를 제거하면서 이 경고도 같이 사라짐.

**변경 내용**: `mix_background_audio()`에서 `title_cues`/`title_seconds` 파라미터, `write_bgm_title_ass()`/`ass_time()` 함수, `build_bgm_track()`의 제목 시각 추적 로직, `--bgm-title-seconds`/`--no-bgm-title` CLI 옵션을 모두 제거. 영상은 항상 `-c:v copy`(스트림 복사)만 쓴다. 실측: 10초 테스트 클립 기준 0.26초(기존 소프트웨어 인코딩 2.73초 대비 10배 이상 단축).

### ★★ 운동용 영상 추출 / 자막·노션·EPUB 분리 + 단계별 소요시간 로그 (2026-07-28)

**문제**: `whisper_series_stream.sh`가 항상 1단계(운동용 고음 영상)와 2단계(자막·번역·Notion·EPUB)를 한 iTerm 세션에서 연달아 돌렸다. 둘 다 매번 같이 도니 총 소요시간이 너무 길어서, 급할 땐 운동용 영상만 빨리 뽑거나 반대로 자막 파이프라인만 따로 돌리고 싶어도 방법이 없었다. 또한 자막 파이프라인 자체가 왜 오래 걸리는지(어느 단계가 병목인지) 로그만 봐서는 알 수 없었다.

**해결**:
1. 2단계(자막·번역·후리가나·Notion·메모앱·MD·EPUB) 로직을 `subtitle_pipeline_body.sh`로 분리했다. `whisper_series_stream.sh`(1단계+2단계 연달아)와 `subtitle_notion_epub_only.sh`(2단계 단독)가 이 파일 하나를 그대로 불러 쓴다 — 로직을 두 곳에 복사해두면 한쪽만 고치고 잊어버리는 문제가 생기기 때문.
2. 새 진입점 3개(shift_alarm 메뉴바에도 버튼 3개로 반영됨):
   - `whisper_series_stream.sh [폴더]` — 기존과 동일, 운동용 영상 + 자막·노션·EPUB **연달아** 실행.
   - `subtitle_notion_epub_only.sh [폴더]` — 운동용 영상 건너뛰고 **자막·번역·Notion·EPUB만** 실행. 새 iTerm 창.
   - `python3 extract_high_pitch_video.py <폴더>` — **운동용 영상만** 단독 추출(원래도 폴더 인자를 지원했음, 별도 메뉴바 버튼으로 노출한 것뿐). shift_alarm에서는 새 Terminal 창.
3. `subtitle_pipeline_body.sh` 안에 단계별 소요시간 로그를 추가했다: 오디오 추출(ffmpeg), Whisper 자막 생성, (번역+Notion 기록+메모앱+이미지캡처) 3문장-루프 전체 및 그 내부 세부(번역/Notion/메모앱/이미지 각각 누적 초), Notion 이미지 업로드, pandoc EPUB 빌드까지 전부 `⏱`로 시작하는 줄로 iTerm 로그에 그대로 출력된다. 실제 병목이 Whisper 자체인지, 번역/Notion API 왕복인지, 메모 앱 AppleScript 호출인지는 추측보다 이 로그로 직접 확인하는 게 정확하다 — 다음 실행 로그를 보고 판단할 것.

### ★ Whisper 자막 생성 속도 튜닝 (2026-07-28)

**배경**: 위 타이밍 로그를 넣기 전부터 사용자가 자막 생성이 체감상 오래 걸린다고 지적. 사용 중인 맥은 M2(퍼포먼스 4 + 효율 4 = 8코어)이고 `whisper-cli --help` 출력으로 Metal GPU와 flash-attention이 이미 기본 활성화되어 있는 것 확인함(이 둘은 더 손댈 게 없음).

**바꾼 것** (`subtitle_pipeline_body.sh`의 whisper-cli 호출):
1. `--beam-size 5` → `--beam-size 1`(greedy). 빔서치는 매 토큰마다 후보 5개를 유지하며 디코딩해 계산량이 greedy 대비 대략 5배 가깝게 든다 — 정확도와 직결되는 트레이드오프라 사용자에게 직접 확인받고 "속도 최우선"으로 결정함. 자막처럼 짧은 발화 단위라 정확도 손실은 크지 않을 것으로 예상.
2. `-p 4`(프로세스 4개, 스레드는 명시 안 해 기본값 4) → `-p 1 -t 8`. 기존 설정은 4프로세스×4스레드=16스레드가 8코어를 나눠 쓰면서, Metal GPU는 하나뿐이라 4개 프로세스가 같은 GPU를 두고 경쟁하는 구조였다 — 프로세스 1개가 GPU와 8코어를 통째로 쓰는 쪽이 더 빠를 것으로 보고 바꿈. 이 부분은 추측 기반 변경이라, 위 `⏱ Whisper 자막 생성 소요` 로그로 실측해서 오히려 느려지면 되돌릴 것(예: `-p 2 -t 4`도 시도해볼 만함).
3. **`--vad --vad-model` 추가 (whisper.cpp 내장 VAD, Silero)**. 사용자가 "무음/신음소리 등 사람 목소리가 아닌 구간을 미리 잘라내고 whisper를 돌리면 안 되나"라고 제안함 — 처음엔 ffmpeg `silencedetect`(에너지 임계값)로 무음만 잘라 압축 오디오를 만들고 whisper 출력 타임스탬프를 원본 시간으로 되돌리는 커스텀 파이썬 코드를 짰었는데, 사용자가 "무음의 기준을 사람 목소리가 아니면 무음"으로 정정 — 에너지 임계값으로는 신음소리(에너지는 있지만 말이 아닌 발성)를 못 걸러낸다. 대신 `whisper-cli --help`에서 whisper.cpp에 이미 Silero VAD(실제로 학습된 음성 감지 모델)가 내장돼 있는 걸 발견해서 커스텀 코드를 전부 버리고 이걸로 교체함:
   - VAD 모델(`ggml-silero-v5.1.2.bin`)은 whisper.cpp 공식 저장소의 `models/download-vad-model.sh`가 가리키는 출처(`https://huggingface.co/ggml-org/whisper-vad`)에서 받아 `/opt/homebrew/share/whisper-cpp/models/`에 둔다. `subtitle_pipeline_body.sh`가 없으면 자동으로 받고, 다운로드 실패(오프라인 등) 시에도 VAD 없이 전체 오디오로 폴백해서 파이프라인이 멈추지 않게 함.
   - **실측 검증**: 무음(2초) + 220Hz 순음(신음소리를 흉내낸 비언어적 발성, 2초) + 무음(2초) + 실제 일본어 문장("こんにちは、これはテストです。", macOS `say`로 합성) + 무음(2초)으로 합성 테스트 파일을 만들어 `--vad --vad-model`로 실행 — 220Hz 톤 구간은 완전히 무시되고 실제 발화 구간(6.11~8.25초)만 정확히 잡혔다. 로그에 `Reduced audio from 163667 to 34240 samples (79.1% reduction)`로 실제 디코딩량 감소도 확인함.
   - **타임스탬프 리매핑이 필요 없다**: whisper.cpp가 VAD로 걸러낸 뒤에도 내부적으로 원본⇄VAD 압축 시간 매핑(`vad_segment_info: orig_start/orig_end` 로그)을 자동 처리해서, 최종 SRT 타임스탬프가 이미 원본 오디오 기준으로 나온다. 그래서 처음 짰던 커스텀 트리밍+리매핑 파이썬 코드는 전부 삭제하고 whisper-cli 호출에 플래그 두 개만 추가하는 것으로 끝남 — 장면 캡처(`ORIGINAL_VIDEO` 절대시간 사용)나 최종 자막 병합 등 하위 로직은 전혀 안 건드려도 된다.

**검증 상태**: beam-size/프로세스 튜닝은 이 세션이 whisper-cli를 실제 영상으로 돌려볼 수 없는 환경이라 로직만 반영했고 실측은 다음 실행 때 확인 필요. VAD 기능 자체는 위 합성 테스트로 실측 검증했지만, 실제 AV 영상(진짜 신음소리·배경음·여러 화자)에서도 기대대로 동작하는지는 다음 실제 실행에서 자막 품질(문장 누락·잘림 여부)과 `⏱ Whisper 자막 생성 소요` 로그로 반드시 재확인할 것.

### ★★ EPUB 생성 실패 — `--epub-version=3` 옵션이 pandoc 3.x에서 삭제됨 (2026-07-23)

**증상**: 로그에 `⚠️ EPUB 생성 실패`만 뜨고 이유를 알 수 없음.

**원인**: 원본 스크립트가 `pandoc ... --epub-version=3 ... 2>/dev/null`로 실행했는데, `--epub-version` 옵션이 pandoc 3.x(사용자 환경: 3.9.0.2)에서 완전히 제거됐다. `pandoc: Unknown option --epub-version.`로 즉시 실패하는데, 에러 출력을 `2>/dev/null`로 버려서 진짜 원인이 안 보였다.

1. `--epub-version=3` 옵션 삭제. `-o *.epub`만으로 이미 EPUB3로 생성되므로 버전 지정이 애초에 불필요.
2. `2>/dev/null` 대신 `${MYTMP}/pandoc_<파일명>.log`로 stderr를 저장, 실패 시 그 로그를 바로 화면에 출력하도록 변경 — 앞으로 비슷한 문제가 생겨도 원인이 바로 보임.

### iTerm 자동화(Automation) 권한 문제 → `.command` + `open -a iTerm` 방식으로 교체 (2026-07-23, 2026-07-24 iTerm으로 재확정)

원본 스크립트는 맨 끝에서 `tell application "iTerm" ... create window ...`로 새 창을 열었는데, 이건 macOS 자동화 권한이 필요하다. 사용자가 직접 터미널에서 실행할 땐 문제없지만, **shift_alarm 메뉴바 앱(launchd 백그라운드 프로세스)에서 호출하면 권한 팝업 자체가 안 떠서 조용히 실패한다** — shift_alarm 프로젝트의 이북리더에서 이미 겪은 것과 동일한 문제(그 프로젝트 README 8-1 참조). 그래서 실행 가능한 `.command` 파일을 만들고 `open`으로 여는 방식으로 바꿨다 — 권한이 전혀 필요 없다.

**★ 2026-07-24 정정**: 처음엔 `open -a Terminal`로 바꿨었는데, 그러면 장면 미리보기(`imgcat`)가 안 보인다는 걸 사용자가 지적함 — `imgcat`은 iTerm2 전용 인라인 이미지 이스케이프 시퀀스라 일반 Terminal.app은 못 그린다. 확인해보니 **`open -a iTerm <파일>.command`도 Terminal과 동일하게 자동화 권한 없이 스크립트를 실행해준다** — 애초에 Automation(`kTCCServiceAppleEvents`) 권한이 필요한 건 `tell application "X"` 같은 AppleEvent를 보낼 때뿐이고, `open`은 Finder에서 파일을 더블클릭하는 것과 같은 취급(Launch Services)이라 대상 앱이 Terminal이든 iTerm이든 상관없이 권한이 필요 없다. 그래서 최종적으로 `open -a iTerm`으로 되돌렸다 — 권한 문제도 없고 imgcat 미리보기도 정상 동작.

### ★★ EPUB 가독성 전면 개편 (2026-07-24)

사용자 피드백: 표지가 이상함 / 전체적으로 가독성이 없음 / 페이지당 글자 수가 너무 적음 / 1편·2편 안에서도 목차 분할이 있었으면 함. 원인과 수정 내역:

1. **표지가 깨져 보이던 원인**: EPUB 안 `cover.xhtml`을 까보면 `<image width="0" height="0">`로 박혀있었다 — ffmpeg가 만든 jpg가 표준 JFIF(APP0) 헤더 없이 저장되는 경우가 있어서 pandoc의 이미지 크기 판독기가 가로/세로를 못 읽고 0으로 처리해버린 것(`file` 명령으로는 정상 JPEG로 보여서 헷갈리기 쉬움 — pandoc이 쓰는 판독기가 더 엄격함). `sips -s format jpeg cover.jpg --out cover.jpg`로 다시 저장하면 표준 JFIF로 정규화되어 해결된다 — EPUB 재빌드 후 `cover.xhtml`에 정확한 `960x1440`이 찍히는 것 확인함.
2. **표지 이미지 자체도 교체**: 예전엔 본문에 쓰던 3장 가로 합성 썸네일(1440x270, 배너처럼 납작함)을 표지로 재사용했다. 지금은 영상에서 별도로 세로 비율(960x1440, 2:3)로 새로 캡처하고, 하단에 반투명 검은 박스 + 제목 텍스트(영상 파일명)를 `drawtext`로 입혀서 표지답게 만든다. 캡처 시점은 영상 길이의 4%(최소 5초, 최대 90초) 지점 — 도입부일 가능성이 높은 이른 시점을 고른 것.
3. **페이지당 글자 수가 적었던 원인**: 장면 이미지가 `width:100%`로 각 세트(대사 3줄)마다 화면 전체 폭을 차지해서, 화면(페이지) 한 장에 텍스트가 몇 줄 안 들어갔다. 이미지를 `38%` 폭으로 축소하고 오디오 플레이어도 `60%`로 줄여서, 같은 화면에 훨씬 많은 대사 줄이 들어가게 했다.
4. **1편/2편 안에서 목차 분할**: 8세트(대사 24줄)마다 "🎬 장면 N" 소제목을 넣어서 EPUB 목차(TOC)에서 장면 단위로 바로 이동할 수 있게 했다. **★ 함정**: 처음엔 raw HTML로 `<h2 class="scene">...</h2>`를 그냥 썼는데, pandoc의 `--toc` 목차 생성기는 마크다운 문법으로 파싱된 `Header` 노드만 인식하고 raw HTML 블록은 그냥 불투명하게 통과시켜버려서 목차에 전혀 안 잡혔다. 마크다운 네이티브 헤더 문법 `## 제목 {.scene}`(pandoc의 헤더 속성 확장 — `{.클래스}`로 CSS 클래스도 그대로 부여됨)으로 바꾸니 목차에 정상적으로 잡힘. `--toc-depth=2`도 추가해서 파트(h1)뿐 아니라 장면(h2)까지 목차에 나오게 함.
5. **개요 페이지 추가**: 각 파트 md 맨 앞(표지/제목 페이지 바로 다음)에 그 파트의 대사 문장 수·장면 수·표기 방식을 요약한 박스를 넣었다. ★ 대사 내용 자체를 AI로 요약하는 기능은 일부러 넣지 않았다 — 성인 영상 대사를 자동 요약하는 파이프라인을 만드는 것은 별개의 판단이 필요한 문제라 통계 기반 개요로 대신함.
6. **검증**: 이미 처리 완료된 `MIAA-444`, `435MFCS-058` 작업 폴더의 기존 md/이미지/오디오를 그대로 활용해(재번역 없이 텍스트만 재구성) 새 스타일로 EPUB을 다시 빌드해서 표지 치수(960x1440 정상)와 목차 중첩(파트 밑에 장면들이 하위 항목으로 들어가는 것) 둘 다 확인함.

### ★★ 본문 중간중간 이미지가 검은 화면/빈 박스로 나오는 문제 (2026-07-24)

표지에서 겪은 것과 **완전히 같은 원인**이 본문 장면 썸네일에도 있었다: `merge_images()`가 ffmpeg로 만드는 jpg 중 일부가 표준 JFIF(APP0) 헤더 없이 저장되고, 그런 파일은 e리더가 가로/세로를 못 읽어서 빈 박스(까맣게)로 렌더링한다. 실제로 확인해보니 **영상 하나 안에서도 세트(장면)에 따라 갈렸다** — `MIAA-444`는 183개 썸네일 전부 헤더가 없었고, `435MFCS-058`은 288개 전부 정상이었다. 정확한 ffmpeg 내부 분기(단일 프레임 `scale`만 쓴 경우 vs 3장 `hstack` 합성한 경우 등)까지 완전히 특정하지는 못했지만, 원인 특정보다 결과를 항상 정규화하는 쪽이 더 확실하고 비용도 낮아서 **`merge_images()`가 만든 파일을 매번 `sips -s format jpeg`로 다시 저장**하도록 고쳤다 — 표지에 이미 쓰던 처리를 세트 썸네일에도 그대로 적용한 것. 기존에 이미 만들어둔 `MIAA-444`/`435MFCS-058`/`AV3` 폴더의 7개 작업물도 이미지 전체를 일괄 `sips` 정규화하고 EPUB을 다시 빌드해서 반영함.

### ★★ 대사 오디오를 "영상에서 자른 실음성" → TTS 합성으로 교체 (2026-07-24)

**문제**: 영상에서 대사 구간(`c['start']`~`c['end']`, 앞뒤 여유 0.15~0.3초)을 잘라 세트별로 이어붙이던 방식이 실제로 들어보면 문장 중간에 끊기거나 빈 공백이 많았다 — whisper가 잡은 타임스탬프가 항상 정확하진 않고, 문장 사이 간격을 그대로 이어붙이다 보니 자연스럽지 않았다.

**해결**: 세트(대사 3줄)를 하나의 문자열로 합쳐서 `edge-tts`(`ja-JP-NanamiNeural`, `-10%` 속도 — `ebook_reader.py`가 영어 TTS에 쓰는 것과 같은 라이브러리)에 통째로 넘겨 mp3를 직접 합성한다. 이러면서:
- 영상에서 개별 문장 오디오를 자르는 ffmpeg 호출, 그걸 이어붙이는 `concat_audio_clips()`, wav→mp3 변환까지 세 단계가 통째로 없어지고 TTS 합성 한 번으로 끝남(코드도 단순해짐).
- 문장 하나하나가 아니라 **세트 단위로 한 번에 합성**하는 이유: 문장별로 3번 따로 합성해서 이어붙이면 그 사이에 어색한 침묵이 생기고, 네트워크 호출도 3배로 늘어난다. 문장을 이어붙인 텍스트를 한 번에 합성하면 자연스러운 억양으로 이어진다.
- **트레이드오프**: 실제 배우 음성이 아니라 TTS 음성으로 완전히 대체된다. 실제 음성도 같이 듣고 싶다면(둘 다 넣으면 세트당 오디오 플레이어가 2개가 되어 페이지 밀도가 다시 나빠짐) 토글 방식으로 확장 가능 — 필요하면 요청할 것.
- 기존에 이미 만들어둔 작업물(`MIAA-444`, `435MFCS-058`, `AV3`의 7개)은 이번에 TTS로 재생성하지 않았다(수백~수천 건의 TTS 호출이 필요해 시간이 많이 걸림) — 실제 음성 오디오를 그대로 유지한 채 검은 화면 버그만 고쳐서 다시 빌드했다. **새로 처리하는 영상부터 TTS가 자동 적용된다.**

### ★ av2 폴더 재작업 — TTS 파이프라인 실전 검증 + 표지 생성 실패 (2026-07-24)

`av2` 폴더(`MKMP-533`, `MUDR-393`)는 급하게 만든 임시 변환 스크립트로 옛 md를 재구성했다가 실패했다 — EPUB을 열면 페이지가 5~6개밖에 없고 내용도 거의 안 보였다(정확한 원인은 못 밝혔지만, 임시 스크립트가 옛 형식을 완전히 정확하게 파싱하지 못했던 것으로 추정). **그래서 임시 변환 대신 실제 파이프라인 스크립트를 처음부터 다시 돌렸다** — whisper 자막(`.wav.srt`)과 장면 캡처는 캐시가 있어서 재사용되고, 번역+TTS+노션+메모+md 생성만 새로 진행됨.

이 과정에서 새 버그 하나 발견: **표지 생성 ffmpeg 명령이 실전 파이프라인 안에서는 조용히 실패**했다(터미널에서 똑같은 명령을 직접 실행하면 항상 성공하는데, 오래 도는 백그라운드 실행 중에는 실패 — 정확한 원인 미확정, 리소스 경합으로 추정). 표지 없이 EPUB이 만들어졌길래 수동으로 표지만 다시 만들어 끼워넣었다. 재발해도 바로 원인을 알 수 있게 `-loglevel error`로 출력을 버리던 걸 로그 파일로 남기도록 고쳤다(실패 시 `⚠️ 표지 캡처 실패 — 로그: ...` 뒤에 마지막 20줄을 바로 출력).

**검증 결과**: `MKMP-533`(76세트, 76개 TTS mp3) / `MUDR-393`(119세트, 119개 TTS mp3) 둘 다 표지(960x1440)·본문 세트 수·오디오 파일 수가 정확히 일치하는 것까지 확인함 — 실제 파이프라인으로 처음부터 다시 도는 것 자체는 정상 동작 확인됨(표지 생성만 예외적으로 방어 로직 추가).
